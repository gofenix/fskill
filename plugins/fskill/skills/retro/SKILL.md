# Retro: 复盘并沉淀改进

首行内联带上 🥷，不要单独起段。

复盘已验证的修复、纠偏和项目模式，把改进沉淀成下次 agent 能复用的上下文；已确认的领域词汇和架构决策也按既有落点记录。不要默认追加到 `AGENTS.md`；先判断内容属于术语、决策还是可执行工程规则。

## 调用边界

首次进入本技能时，须由用户显式输入 `/retro`、`$retro`、`调用 fskill 的 retro`、`用 fskill retro skill`、`invoke fskill retro`、`use fskill retro skill`，或 Desktop 根分发器已从 `/fskill retro` 选中本技能，或当前会话里用户已进入 `/f-mode` 且 f-mode 点名了本技能。同一任务中的回答、补充、纠正和继续请求沿用已显式调用的技能，无需每轮重复命令；f-mode 关闭时，新任务或切换技能仍需显式调用；f-mode 开启时可由 f-mode 按当前目标重新选择。若宿主仅因语义相似自动加载本技能，不应用下文流程，按普通 Agent 请求继续处理。

## 交付约定

- 目标: 用户得到一份明确的沉淀结果：已安全写入、需要确认、或明确不沉淀，并说明原因。
- 完成条件: 每个候选经验、术语或已定决策都被分流到正确层级，重复规则被合并，私有或一次性信息被过滤，下一次 agent 能发现它；新增防错检查有正反例证据或明确验证缺口。
- 依据: 本轮已验证的修复或审查结果、用户纠偏、当前仓库指令、已有 docs/rules/references/tests、必要 git diff 和验证日志。
- 交付形式: 按候选经验列出落点、改动、原因和验证；如果需要修改文件，先说明具体目标文件和最小编辑。

## 长期上下文预检

可选读取长期上下文，但只作为背景。对 `/retro` 来说，旧记忆可以提供反复出现的纠偏、历史失败模式和用户长期偏好；当前仓库状态、用户纠偏、diff、测试、日志、文档和公开指令优先于旧记忆。

不要读取原始会话记录，除非用户明确要求从历史会话里提炼教训，或当前摘要不足以还原关键失败模式。即使读取了历史，也只沉淀可验证、可复用、可公开的规则。

## 模式选择

| 用户意图 | 模式 |
|---|---|
| 已解决问题、用户纠偏、发布教训、防复发经验 | 经验复盘模式 |
| 沉淀已确认的术语、领域词汇或领域边界 | 已确认上下文沉淀 |
| 记录已经确定且难以逆转的架构决策 | 已确认上下文沉淀的 ADR 筛选条件 |

设计方案还没有确定时可建议用户显式调用 `/think`，不自动切换。`/retro` 只沉淀已确认的术语和决策，不主动开展领域建模。

## 经验筛选

只有同时满足三点，才值得写进长期文档：

1. 这个错误或模式很可能再次发生。
2. 这条规则会改变 agent 下一次行为。
3. 它能写成可验证或可执行的规则，不依赖一次性上下文。

不满足时，不写入仓库；只在最终答复里短暂记录。

## 沉淀授权边界

满足调用边界后，才检查本任务是否出现这些信号：

- 用户纠偏了 agent 的实现方式、测试方式、日志 API、分层边界或命名约定。
- 修复暴露了项目特有约束，而当前 `AGENTS.md`、规则、测试或文档没有写。
- 同一类错误可能在新会话重复发生。
- 这条经验能写成下次 agent 可执行的正向规则。

先区分评估与沉淀请求：仅评估候选、询问建议或明确要求不改文件时，只输出评估，不执行创建或编辑。用户已要求沉淀且授权仍有效时，再应用上述筛选条件；没命中不写，命中且落点明确、内容不含私有信息时直接做最小安全编辑。不确定或超出授权范围时先问。

## 已确认上下文沉淀

先读取项目已经使用的术语和决策文件，再决定落点：

1. 已有 `CONCEPTS.md` 或 `CONTEXT.md` 时沿用；两者都存在时，优先使用被 `AGENTS.md`、README 或当前模块文档引用的文件，仍有冲突再问用户。都不存在时，以根目录 `CONCEPTS.md` 为建议落点；实际创建遵循沉淀授权边界。
2. 术语文件只写项目特有的领域概念、简短定义和需要避免的同义词。实现方案、测试规则、日志 API 和代码分层不放进去。
3. 用户说法和现有词汇或代码行为冲突时，指出具体冲突并确认哪个才是当前事实，不静默覆盖。
4. 只有决策同时满足“难以逆转、脱离上下文会令人困惑、经过真实取舍”时才写 ADR。
5. ADR 沿用项目现有目录和模板；没有约定时写入 `docs/adr/NNNN-slug.md`，编号递增，正文用 1 到 3 句话说明背景、决定和原因。

如果项目已有多上下文映射或模块级术语文件，按现有导航写入；不要为了这次沉淀新造一套上下文映射。

## 落点选择

| 落点 | 适用内容 |
|---|---|
| `AGENTS.md` / `CLAUDE.md` | 当前项目所有 agent 必须长期遵守的硬规则、仓库地图、验证入口、发布边界 |
| `docs/solutions/` | 已解决问题的症状、失败尝试、根因、解决方案、预防方式 |
| `CONCEPTS.md` 或现有 `CONTEXT.md` | 项目特有的领域词汇、简短定义和需要避免的同义词，不含实现决策 |
| `docs/adr/` 或现有 ADR 目录 | 难以逆转、缺少背景会令人困惑且经过真实取舍的已定决策 |
| `rules/anti-patterns.md` | 跨项目通用 AI 失败模式，且适用于所有 fskill 技能 |
| `skills/<name>/references/` 或常见误区 | 某个技能专属的操作经验、审查重点或写作/设计规则 |
| `scripts/` 或 `tests/` | 可以被确定性检查自动阻止的错误 |
| 不长期写入 | 单次偏好、临时环境问题、未验证猜测、私有路径、token、内部系统或过细事故叙事 |

重复错误或高影响违规需要结构性防复发时，读取 [结构性防复发](references/structural-prevention.md)，选择最小有效层并验证它确实阻止过去的错误。日志 API、分层或测试方式等纠偏先判断能否由现有结构与工具约束；需要人判断的部分才留在规则与导航。

## 复盘流程

1. **收集候选**：从本轮用户纠偏、已修复 diff、失败日志、审查发现或发布事故中提取候选经验；导航困难、工具开销、信息访问和无效指令仅在会话证据表明确实影响执行时纳入，不因缺某种配置就制造发现。
2. **核对已有上下文**：读取相关 `AGENTS.md`、`CLAUDE.md`、`rules/`、`docs/solutions/`、`CONCEPTS.md`、`CONTEXT.md`、ADR、相关技能参考和测试入口，确认是否已有同义规则。机械错误先核实已有 lint/test/hook/CI 是否生效；检查存在但未接线或损坏时优先修原入口，结构性防错按上述参考处理。需判断的约束放到相应 reviewer 或工作流，不强行做成正则检查。
3. **提炼**：去掉事故叙事、私有事实和一次性命令，把经验压缩成可复用规则或解决方案。
4. **选择落点**：按“落点选择”确定唯一主位置；如果需要两个位置，一个负责发现入口，一个负责详细内容。
5. **编辑或报告**：按沉淀授权边界区分只读评估和已授权写入；目标文件不明确、规则影响面大或可能污染公共上下文时先问。
6. **验证可发现性**：确认下一次 agent 会在合理工作流里找到规则与实际执行入口；只读评估时报告导航缺口，已授权沉淀时才补最小导航，不复制详细经验。复杂复盘且证据足够时，可用反向视角检查遗漏的失败解释、下游影响和验证漏洞；它用于挑战结论，不要求固定 reviewer 数或自动新增待办。

## 硬性规则

- 不要机械追加到 `AGENTS.md`；`AGENTS.md` 只放长期硬规则和导航。
- 先合并已有原则，再新增条目；同义规则必须折叠。
- 不把私有路径、token、内部系统、会话 ID、个人机器配置写进公共文件。
- 不把未验证猜测沉淀成规则；写成“需要验证”不算可长期复用的经验。
- 不把实现方案写进领域词汇文件，也不把尚未决定的方案写成 ADR。
- 能用测试或脚本防住的错误，优先建议验证器，不只写文档。
- 一次只推荐最小必要改动；超过 3 个目标文件时先说明为什么不能更集中。
- 用户已授权沉淀且落点清楚时，不要只建议“以后注意”；把规则沉淀到下一次 agent 会读到的位置。

## 常见误区

| 情况 | 规则 |
|---|---|
| 用户说“更新 AGENTS” | 先判断是否真的属于项目硬规则；不属于就改去正确层 |
| 修复刚完成但没验证 | 先要求或运行验证；未验证不沉淀为事实 |
| 经验只对当前机器成立 | 不进公共仓库；可放本地记忆或最终答复 |
| 已有规则说过同一件事 | 更新原规则措辞或示例，不新增平行条目 |
| 规则会让 agent 过度保守 | 写触发条件和反例，避免所有任务都被阻塞 |

## 输出

如果只是评估，输出：

- **保留**：值得沉淀的候选经验和原因。
- **不沉淀**：不写入长期文档的内容和原因。
- **落点**：每条经验应该落到哪里。
- **下一步编辑**：最小编辑计划或明确说无需编辑。

如果已完成编辑，输出：

- **已沉淀**：写入了什么、写到哪里。
- **落点原因**：为什么是这一层。
- **验证**：运行过的检查，或剩余验证缺口。

已确认上下文沉淀时输出：

- **术语**：新增、修改或确认的领域词汇。
- **决策**：写入的 ADR，或未达到 ADR 筛选条件的原因。
- **冲突**：词汇、用户说法和代码是否一致。
- **验证**：下一次 agent 会从哪里发现这些内容。
