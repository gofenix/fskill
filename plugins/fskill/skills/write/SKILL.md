# Write: 去掉 AI 味

首行内联带上 🥷，不要单独起段。

把文案改到自然、有人的判断，但不炫技。不要“提升词汇”，要去掉表演式改进。

## 调用边界

首次进入本技能时，须由用户显式输入 `/write`、`$write`、`调用 fskill 的 write`、`用 fskill write skill`、`invoke fskill write`、`use fskill write skill`，或 Desktop 根分发器已从 `/fskill write` 选中本技能，或当前会话里用户已进入 `/f-mode` 且 f-mode 点名了本技能。同一任务中的回答、补充、纠正和继续请求沿用已显式调用的技能，无需每轮重复命令；f-mode 关闭时，新任务或切换技能仍需显式调用；f-mode 开启时可由 f-mode 按当前目标重新选择。若宿主仅因语义相似自动加载本技能，不应用下文流程，按普通 Agent 请求继续处理。

## 交付约定

- 目标: 文案保留作者意图，同时更符合目标读者、场景和语言习惯。
- 完成条件: 除非用户要求改变事实或结构，否则意义、事实主张和结构被保留，AI 腔被去掉；文件级审稿时明显标点问题已检查。
- 依据: 用户提供的文本、目标读者、项目风格参考、当前发布或产品状态和目标语言。
- 交付形式: 默认只给改好的文案；只有用户要求时才给说明、变体或审阅意见。

## 核心立场

这个技能是气味目录，不是逐条执行的检查清单。识别 AI 味后做判断：该删就删，该保留就保留。

- **过度编辑和编辑不足一样失败**。句子已经自然、清楚、稳定时，不要动。作者自己的成稿默认只修错字、病句和明确的 AI 腔，不为风格重写。
- **作者声音优先**。保留作者原有口语、节奏和立场。情绪、个人判断和写作缘由也是内容，不因抽象或抒情就删除、改淡或要求外部证据；拿不准时保留。规则是默认值，不是法律。
- **禁用词表和替换表只是例子**。看气味，不做机械查找替换。
- **少而准**。三个有效改动比三十个机械替换更好。

把新经验沉淀进技能时，合并到已有原则，不要无限追加同义禁用词。

## 编辑前检查

1. **改写还是新写？** 改写时先读取用户提供的文本或指定文件；两者都没有才请求原文。新写时读取指定素材并按先有素材，再谈篇幅推进，不要求先有草稿。仅审稿时输出问题和建议，不写回文件。
2. **读者是否明确？** 读者不能从请求、素材或文本推断且会影响写法时先问。
3. **目标语言**：遵循用户明确指定的目标语言；未指定时，改写保留原文语言，新写沿用任务的语言约定。按目标内容选择参考：
   - 中文 + 发布说明或社交发布：读取 `references/write-zh-release-notes.md`
   - 中文 + 双语文案或翻译审阅：读取 `references/write-zh-bilingual.md`
   - 产品/网站/app 本地化：读取 `references/write-product-localization.md`；有中文时也读 `references/write-zh-bilingual.md`
   - 默认中文正文：读取 `references/write-zh-prose.md`；需要完整模式库时读 `references/write-zh.md`
   - 其他情况：读取 `references/write-en.md`
4. **技术说明**：安装步骤、操作说明、错误文案、工具描述和 Agent 指令的措辞修改，同时读取 `references/write-technical.md`。混合文章只对相关段落应用，不扩展为技术正确性审查或提示词流程设计。

发给他人的问卷、PR body、技术文档目的选择，或从零收集长文素材与安排读者理解顺序时，按需读取 `references/write-deliverables.md` 的对应部分；不把收件人问题变成对作者的技术访谈，也不把起草当发送授权。

读取对应参考后再改。默认不解释修改。

## 标点检查

先把 Write 资源目录解析为绝对路径 `SKILL_DIR`：独立安装时为本技能入口所在目录，Desktop 合包时为包根目录下的 `skills/write`。运行其随附脚本，待审文件仍使用目标项目路径。

当用户要求审稿、润色文件、发布文案或本地化文案审阅，且文本来自文件或会被写回文件时，运行：

```bash
bash "$SKILL_DIR/scripts/check-punctuation.sh" --lang auto <file>
```

脚本只检查明显标点问题：中英文/日文标点混用、em dash、全角空格、中英数字间缺空格。它会跳过代码块、行内代码和 URL。短消息直接改写时，不需要为了跑脚本创建临时文件。

## AI 味检查

当用户要求中文文件级审稿、去 AI 味、发布文案或本地化文案审阅，且文本来自文件或会被写回文件时，可以运行：

```bash
bash "$SKILL_DIR/scripts/check-ai-flavor.sh" --lang zh <file>
```

脚本只扫描明显结构外壳：二分对照、机械先后、本质拔高、助手路标、泛互动结尾、冒号模板、过密 `X 很 X`、表格内容复读表头。它会跳过代码块、行内代码、URL 和引用块。结果只辅助判断，不替代人工改稿；短消息直接改写时，不需要为了跑脚本创建临时文件。

## 长期上下文预检

可选读取长期上下文，但只作为背景。对 `/write` 来说，旧记忆可以提供声音、格式和用户偏好；当前提供的文本、目标读者、项目文档、发布状态和来源材料优先于旧记忆。

## 硬性规则

- **原意优先，风格其次。** 保留作者的意思、情绪、立场和有意的表达；去 AI 味不能把个人声音改成通用文案。署名引用和推荐语默认逐字保留，只有明确纳入改写范围才改，并区分转述与原话。去推广不等于删除正常产品说明、许可信息或相关产品介绍。恢复误改原文时，沿该段 diff 找到误改前最近版本并逐字核对，不选更旧、更短的版本或改动无关段落。
- **作者声音有来源。** 代笔中的经历、意见和引用必须来自作者提供或已发表的材料；修辞不合适时优先删减，不补造经历或意象。作者明确用于本文的背景可以保留；面向目标读者未授权披露的敏感信息先确认。
- **先有素材，再谈篇幅。** 新写长文前，确认每个章节都有不同的事实、经历、数据或来源支撑。素材不足时先研究、集中问必要问题或缩短篇幅，不为凑字数反复改述同一观点。编辑现成文章不设机械删减比例。
- **审语言表达，不审技术正确性。** 只审语言、表达和结构；技术方案、PRD、spec 的正确性、一致性和可实现性审查可建议用户显式调用 `/check`，不自动切换技能。
- **结构调整有授权。** 不擅自重排标题、段落、顺序或合并章节，除非用户要求。长文编辑模式例外。
- **事实主张基于产物。** 发布文案、发布说明、产品页和公开回复的事实必须来自当前产品、可运行产物、截图、发布页、变更记录、issue/PR 或用户材料。
- **不用长破折号。** 新写或在授权范围内改写的文案不用 U+2014 或 U+2013，改用逗号、句号、冒号、分号或括号。
- **匹配交付方式。** 粘贴文本的润色默认只给改稿；文件编辑给出范围内的改动与验证，并完成用户已明确授权的 commit/push。输出简洁不能掩盖未完成的交付。

## 长文编辑模式

长文（约 300 行以上，或多个 `##`、表格和图片）里，最大问题通常是结构重复，而不是单句不自然。

流程：

1. **先只读梳理。** 先读完整文章，列出 `##` 章节、表格、列表和图片。标出三类问题：跨章节重复、复读表格、整段/整节冗余。
2. **用变更点提出删改。** 每个结构删改都给改前 -> 改后；用户尚未授权结构调整时先确认，已明确要求重组或删减时直接完成范围内修改。
3. **再逐句去 AI 味。** 在已确认范围内逐节去 AI 味，复查删去的段落是否包含唯一事实、情绪或限制。
4. **交付变更点。** 默认给变更点，不直接吐整篇重写稿。用户说“直接改”时才输出完整改稿。

不要单轮重写 4 万字文章，那会覆盖作者手调的表达，也很难审阅。

## 双语审阅模式

用于中英混排、中文文案、双语一致性、发布说明。

规则：

- 中文和英文之间通常留空格，品牌名、命令、路径和代码除外。
- 不把英文术语硬翻译成别扭中文；必要时保留英文。
- 中英版本要事实一致、语气一致、编号一一对应。
- 发布说明要工程师可读，不做营销腔。
- 社交文案可以更口语，但不能夸大事实。

## 产品本地化模式

用于产品 UI、网站、应用商店、设置项、按钮、空状态、错误提示等本地化。

检查：

- 文案是否符合控件大小和状态。
- 是否把功能承诺说过头。
- 中文是否自然，英文是否符合自然的产品文案习惯。
- 多语言是否保持同一事实，不逐字硬译。
- 错误提示是否告诉用户下一步，而不是只解释失败。

参考 `references/write-product-localization.md`。

## 英文编辑

英文编辑时不要把文字变得更“高级”。目标是更自然、更准确、更像人写。

优先：

- 删掉总结腔和过度连接词。
- 把抽象名词改回具体动作。
- 保留作者的直接语气。
- 避免 em-dash、过密形容词和“not only... but also...”式模板。

参考 `references/write-en.md`。

## 输出

写作或润色交付前，按语义识别并剔除写给作者或 AI 自己看的备注，包括核验待办、补充提醒、素材评价和编辑建议。整句备注直接删除；与正文混在同一句时，只删备注部分并接顺正文。保留正文必要的事实限制、有效引用及用户明确要求的批注，不因清理备注而改变事实主张或其确定程度。

默认只输出清理后的文本本身，不把删掉的备注移到文末或单独列出，也不额外提示“已删除备注”。用户要求审阅时，输出：

```text
结论：...

主要问题：
- ...

建议改稿：
...
```

用户要求多个版本时，最多给 3 个，并说明每个版本的使用场景。
