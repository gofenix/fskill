# 模块、接口与测试接缝

在评价候选或深入已选边界时读取。以下词汇用于准确说明结构，不要求替换项目本来的类名、服务名或领域语言。

## 评估的对象

| 概念 | 这里的含义 |
|---|---|
| 模块 | 拥有接口与实现的行为单元，可小至函数、大至包或跨层业务切片 |
| 接口 | 调用方为正确使用它必须知道的全部信息，含签名、语义、错误、不变量、顺序、配置与性能承诺 |
| 深度 | 调用方学习少量接口知识后能可靠取得多少行为；不按实现行数与接口行数的比例衡量 |
| 接缝 | 能替换行为的具体位置，需单独判断放在哪里，以及隐藏什么 |
| Adapter | 在接缝处满足约定的具体实现；生产传输与测试替身都可能承担此角色 |
| 变化集中度 | 一项规则变化或缺陷修复是否主要留在一个地方，而非要求多个调用方同步修改 |

一个模块可以在外部提供简单接口，内部保留小部件与测试接缝；深化不等于把实现揉成一大段代码。

## 表示与所有权

从真实不变量和访问方式选择表示。互斥状态用可区分的变体或状态转换集中表达，避免多个布尔与可选字段让矛盾组合合法；重复规则收回单一所有者。清楚而局部的分支无需新抽象。只有操作原本无法覆盖某种输入、必须靠断言或“不会发生”异常继续时，才考虑强化类型或修改结果契约；不为更精确而增加层次。

外部原始输入与已验证模型分开，在实际入口解析并尽量从权威 schema 派生形状，防止协议细节扩散到调用者。表示必须真的排除所声称的非法状态：字段改名或把范围写成起点加普通数值，仍不能排除负数等非法值。类型不能代替并发、持久化或状态变化后的有效性检查；内部约束也不能无条件删除。

多个参与者可能写同一对象时，先判断它们是在发布独立事实，还是确实维护一个规范状态。独立事实优先分离写目标，在读取或汇总处合并；写同一 JSON 的不同字段仍是共享修改。确需共享对象才按真实存储语义选择 single writer、锁、事务或 compare-and-swap，并验证冲突与中断行为；一句 ownership 说明不是并发控制。

## 假想删除与调用方知识

想象删除候选模块但保留其行为需求：

- 复杂度随之消失，调用方还能同样工作：它可能只是转发或多余间接层。
- 同样规则重新散落到多个调用方：它确实隐藏了复杂度，应保护这部分职责。
- 规则本来已泄漏到调用方：考虑把知识收回，或把接缝移到更合适的位置。

删除只是思维检验，不是删除代码的授权。把结论落实到真实调用例子：调用方目前必须知道哪些步骤，改后可以忘掉哪些信息。接口方法少，但要求用户自己保持事务、缓存、幂等或错误顺序，仍可能很浅。

## 依赖与测试方式

分类是选择验证方式的起点，不是“某类依赖一定可以合并”的定论：

| 依赖 | 可用验证方式 | 需要保留的限制 |
|---|---|---|
| 进程内计算或内存状态 | 通过行为接口直接测试 | 合并仍需考虑所有权、复杂度与变化方向 |
| 可在本地替代的 I/O | 用本地数据库、文件系统或其他替身覆盖模块行为 | 替身与生产在事务、时序或特性上的差异需要单独检查 |
| 远端但由团队控制的系统 | 在合适接缝注入传输 adapter，并验证协议与行为约定 | 内存 adapter 不能证明真实网络集成成立 |
| 真正外部的第三方系统 | 在外部接缝使用 mock 或受控 sandbox，保留契约验证 | mock 只证明己方假设；外部实际行为仍需相应证据 |

生产实现与真实需要的测试替身可以证明一个接缝有价值；未出现实际变化或验证需求时，不额外切一层 port。内部接缝可以用于有意义的实现测试，无须暴露给外部调用者。

主要行为应能通过公开接口验证，断言可观察结果，避免把内部调用顺序当契约。迁移时先确认旧测试覆盖的独立行为，补足新接口覆盖后再删除重复或失效测试；不以“所有测试必须只测外部”否定必要内部检查。

## 比较备选接口

只有真实取舍尚未解决时，才做 design it twice。先固定行为、约束、依赖和至少一个真实消费者，将成功条件变成适用的比较标准，例如调用方知识、不变量、变化集中度、可验证行为和迁移成本；再选能够揭示差异的设计方向。

每份设计给出：

1. 同一个真实调用场景的用法，先从消费者实际需要的操作与结果出发。
2. 从用法推导的接口草图及不变量、顺序与错误语义，核对表示能承担真实访问方式。
3. 实现隐藏的复杂度，以及仍由调用方承担的知识。
4. 依赖和测试接缝、迁移成本与不足。

独立尝试使用同一问题、约束和事实，各自给出理由与被拒绝路线；产生候选期间不互相抄结论。比较几份接口草图足够时，不写多份实现；并行只在有授权和工具能力、且独立视角确有帮助时使用，不要求固定 agent 数量。

候选完成后完整读其产物，逐项按预定标准比较；缺失产物或没有覆盖的标准标为缺口，不能算通过。选择基底时说明理由，必要时融合其他候选的兼容优点，同时记录采纳、拒绝与分歧的裁决依据。保持现状也是有效备选，共识不是正确性证明。

融合后重新检查同一标准、不变量、调用示例与必要行为证据；多个分别成立的设计片段不能证明组合成立。只获准设计时交付草图与待验证事项，不把评审推荐转为实施授权。

## 迁移与重新设计

已授权重构时先固定必须保持的行为，并盘点真实消费者、生成物和相关测试。全部调用者可协调迁移且没有外部兼容承诺时，同一迁移范围内收敛旧入口，避免留下会继续被复制的重复路径。跨部署、已发布客户端或外部消费者不能同步时，按兼容要求分阶段 expand–contract，说明过渡层的消费者、验证、回滚与退出条件；不为尚未发布的接口虚构迁移需求。

实施持续出现同形绕路、重复特殊分支、强制断言或调用者必须补守内部规则时，回查新证据是否挑战原设计；单个合理边界情况不自动触发重构。确需重开时，把已发现约束视为设计输入，重新比较更小的可行形状，而不是继续拼补旧草图。变更范围、可部署提交与集成门槛沿用项目约定和既有授权，不以“重新设计”为由破坏现场或扩大任务。
