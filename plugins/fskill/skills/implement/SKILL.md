# Implement: 把批准任务图集成到可验收状态

首行内联带上 🥷，不要单独起段。

由一个协调者持有规格、任务图和集成状态，安排可开始的票，验证合入后的行为，再解锁下游，直到批准范围全部交付或留下可恢复的明确阻塞。

## 调用边界

首次进入本技能时，须由用户显式输入 `/implement`、`$implement`、`调用 fskill 的 implement`、`用 fskill implement skill`、`invoke fskill implement`、`use fskill implement skill`，或 Desktop 根分发器已从 `/fskill implement` 选中本技能。同一任务中的回答、补充、纠正和继续请求沿用已显式调用的技能，无需每轮重复命令；新任务或切换到其他技能仍需显式调用。若宿主仅因语义相似自动加载本技能，不应用下文流程，按普通 Agent 请求继续处理。

## 交付约定

- 目标: 在一个明确的集成分支上交付已批准任务图，并准确报告代码、验证和 tracker 的各自状态。
- 完成条件: 每票验收都有合入后的验证证据，最终集成满足规格与项目必要检查；授权范围内的 tracker 操作已读回，未授权或阻塞的收尾明确列出。
- 依据: 已批准规格与票据、blocking DAG、当前 Git/worktree 状态、仓库指令、实际验证结果、已有 tracker 映射和本轮协调账本。
- 交付形式: 集成分支与 commit、逐票状态和证据、最终验证、tracker 读回结果，以及仍待处理的阻塞和恢复位置。

## 模式与资源

| 情况 | 处理 |
|---|---|
| 首次实施批准任务图 | 建立协调账本与集成基线，再安排可开始的票 |
| 重复启动、中断恢复或接手 | 先读回原协调者、活跃执行者、worktree、合入 commit 和验证，不重复派工 |
| 单节点任务图或没有 delegation 能力 | 串行完成，保留相同的 claim、合入与验证条件，不强制额外 worktree |

进入实施或恢复前读取 [编排与恢复](references/orchestration.md)。只有用户要求 test-first、风险需要回归测试或现有测试需要扩展时，读取 [行为验证](references/testing.md)；TDD 不独立成技能，也不强制用于每张票。

先读取项目已有 `AGENTS.md`、相关 docs 和 tracker 映射，沿用领域术语、验证入口和已有批准。缺少 tracker 配置时用本地 Markdown 与协调账本，不要求 setup。缺少已批准范围或可验收票据时，指出最小缺口；不把普通代码请求自行扩展成任务图编排。

## 实施流程

1. **核对批准与当前状态**：读完整规格、票据和相关评论，确认批准范围、已定接口、测试边界、分支与 dirty 文件归属。重复启动按 [编排与恢复](references/orchestration.md) 接续现有执行；同一任务已有实施授权时不重复批准。
2. **建立可开始的前沿**：维护唯一协调账本，校验 ID、依赖和环路；仅依赖均已通过合入验证的未认领票可以开始。使用本技能附带的 [任务图检查器](scripts/task_graph.py) 检查账本；脚本路径从已加载技能目录解析，独立安装和 Desktop 合包都使用附带脚本，不从目标项目找同名程序。
3. **认领与派工**：先保存 owner、票 ID、基线 commit 和共享文件 ownership，再执行或委派。可用且获授权的 delegation 按前沿并行；每个并行实施者在基于集成分支的独立分支/worktree 工作，收到规格、票据、接口和验证的指针。共同写入文件必须指定单一 owner 或串行，不能等冲突后才分工。
4. **收取单票交付**：实施者提交行为、commit、验收结果和限制；`done` 只表示提交待集成。核对工作基于正确集成线、变更在票据范围内且必要检查通过；基线过旧时按恢复规则同步，不 reset 未知 dirty worktree。
5. **串行合入并验证**：由唯一 merger 角色把单票合入集成分支，记录合入 commit；在合入后的实际 revision 上运行本票与受影响依赖的必要验证。只有通过后才写 `verified` 并重算前沿。合入失败、测试失败或证据失效时冻结受影响下游，修复并重新验证，不让执行者的“完成”越过集成门槛。
6. **完成规格并收尾**：所有票通过后，验证最终集成行为和项目要求的检查，按项目既有审查要求审阅实际 diff 并处理发现。只有本任务已授权的 push、PR、关闭票据等外部动作才执行并读回；清理仅限账本记录的本任务 worktree 且确认无未保存工作，否则保留并报告恢复位置。

每轮前沿变化都由同一个协调者处理。执行者结束或一个合入完成后继续安排剩余票，不重新创建一轮协调会话来接管同一图。

## 硬性规则

- 单票 `done`、合入、集成 `verified`、tracker 关闭是四个不同事实；下游只由集成验证解锁。
- 一次任务图只有一个活跃协调者和一个串行 merger；角色可以由同一 agent 承担，无 delegation 时直接串行。
- worktree 创建、分支基线和 ownership 以实际 Git 读回为准；不 reset、覆盖或删除来源不明的改动与目录。
- 已授权范围内持续推进；新范围、不可逆操作或尚未授权的外部动作遵循本任务授权边界，不把 tracker 配置视为授权。
- 状态账本保存事实与证据指针，记录中断点；验证器只能检查账本一致性，不能把状态字符串变成真实运行证据。
- 不自动调用其他技能，不为套流程强制并行、全量测试或创建 PR。

## 常见误区

| 情况 | 规则 |
|---|---|
| 执行者报告完成就派下游 | 先串行合入、运行必要验证，再写 `verified` |
| tracker 已关闭但没有集成证据 | 读回代码与验证，不能据此满足 blocking |
| 两票改同一生成文件或 lockfile | 指定单一 owner，其他票交付源改动；合入后统一生成与验证 |
| 恢复时又创建一批相同执行者 | 先核对 owner 和活跃派工，接续或明确移交后再认领 |
| 一张小票也开多个 worktree | 用单节点串行路径，保留验收与集成记录即可 |

## 输出

- **交付**：规格、集成分支与最终 commit；已合入并验证的票。
- **证据**：本票验证、最终集成验证及未覆盖条件，区分执行者结果与合入后结果。
- **tracker**：实际更新/关闭/PR 状态与读回；没有授权的动作仍列为待办。
- **恢复**：未完成票、owner、阻塞、保留 worktree 和下一次应接续的位置。
