# 代码系统与历史决策

研究一个系统如何运行，或为何形成当前设计时读取。先锁定问题、代码范围、适用 revision 和调查预算；不把机制说明扩成重构，也不把历史解释写成作者意图的猜测。

## 建立可核查的运行模型

从真实入口追踪一次行为：触发者、输入、调用与状态变化、持久化或外部交互、返回和失败分支。沿调用读取实现和相关测试，不靠文件名、接口声明或旧文档补全缺失边。

围绕读者的问题说明关键概念、数据与控制流、模块所有权和边界；引用关键符号及位置。图示只用于解释关系，不堆完整目录或逐行翻译源码。复杂系统可以按独立角度调查，最后核对交界处；无法连起的路径明确列为缺口，不因多个摘要一致就视为已证实。

完成条件：读者能沿引用还原目标行为，知道状态由谁改变、边界接收和交付什么，以及哪些路径尚未查明。当前实现能证明行为，不能单独证明业务期望或历史动机。

## 追踪历史动机

1. **建立锚点**：定位目标行、关键符号、相关提交和 PR 或票据。按问题使用 `git blame`、跟随重命名的历史、`git log -S` / `-G` 与提交 diff；最近一次修改不一定是设计来源。
2. **按线索选来源**：先读提交、PR 正文与讨论、相关测试和已有 ADR，再沿线索查询可用的票据、文档、团队讨论，或与当时事件相关的运行和分析记录。限定主题与时间，不要求每次遍历所有来源，也不假定特定 forge、MCP 或工具已可用。
3. **保存搜索覆盖**：对实际选择的来源记录查询、时间窗口、读过的条目与定位指针，区分找到证据、没有匹配、无权限或不可用、保留期不足。只看标题或搜索摘要不能代替阅读全文；关联材料超出范围时留作线索。
4. **比较记录**：检查来源日期、当时是否只是草案、后来是否撤回或被替代。相互转引不是多份独立证据；矛盾并列呈现，不选最顺的叙事。用户提供的解释也是待查假说。

按证据强度组织结论，保留各自主张的确定程度：

| 层级 | 含义与交付 |
|---|---|
| 直接证据 | 当事记录明确说明原因，引用具体文本与位置 |
| 支持性证据 | 多项独立间接证据收敛，说明各自贡献和仍未直接证明的部分 |
| 推断 | 列明依据和推理步骤，使用“可能”“与此一致”等措辞 |
| 竞争假说 | 多种解释仍成立，给出各自支持、反证或可区分的缺失证据 |
| 未知 | 说明哪个问题未解、查过什么、哪里不可查询，不用合理故事填补 |

错误计数下降、监控阈值相同或发布前后时间吻合只能提供相关性；排除同期变化、采样、重新分组和观测变化前，不能断言具体改动造成结果。代码、测试和指标可以约束解释，只有确实记录动机的内容才直接证明动机。

完成条件：历史主张有可追溯来源，推断与竞争解释清楚，搜索覆盖和未查明部分可供读者复核。原理由是否仍适用需要当前事实，不能由“当时这样决定”自动推出。

## 转为后续工作的输入

调查是改动前置时，把有证据的发现压缩为四类输入：

| 输入 | 内容 |
|---|---|
| Preserve | 仍有效、必须保留的行为或约束及证据 |
| Change | 已被当前证据挑战、值得重新决定的部分，不把建议写成已批准变化 |
| Avoid | 已知失败路线及失败条件，保留其适用范围 |
| Risk | 尚未查明、可能影响改动的假设与验证办法 |

这些输入交给后续决策或已授权实施，不自动调用其他技能、重开已有 ADR、发送消息或修改代码。沿用项目笔记位置；临时答复不制造长期档案，公开产物不携带私有讨论或敏感原始数据。
