# 工程原则

这些是动手时的立场，不是失败模式清单。失败模式在 `anti-patterns.md`。两边不重复同一句话：反模式表负责「声称完成却没有证据」；这里只要求证据来自真实路径，而不是代理信号。

原则约束全部核心技能。能放进 references 或规则的，不要再开一个技能。

| # | 原则 | 怎么用 |
|---|---|---|
| 1 | 少写能解决问题的代码 | 用最少的代码和层次达到结果。能删掉的传递、重复决策和「为以后」的分支，先删。diff 变小通常比结构变巧更好。 |
| 2 | 先减后加 | 演进系统时先去掉不赚钱的复杂度，再加新东西。按真实用法设计，不为想象中的边界加校验、解析器和开关。 |
| 3 | 看真实路径 | 证明一件事做成了，要跑用户会走的那条路径。编译通过、文件时间、缓存截图和自我报告都只是代理。验证失败时先怀疑观察方法。 |
| 4 | 修根因 | 先复现，再追到第一个真正出错的点。用判空、重试或注释把症状压下去，会把根因留在系统里。同一种坏模式出现多次时，一次修完。重启后才坏，先怀疑缓存、锁和序列化状态。 |
| 5 | 降低读者负荷 | 维护成本是读者要穿过的层数，加上要记住的状态。过路层、单实现适配器和没有压缩能力的接口应当收掉。新读者应能很快回答「X 从哪来、谁能改它」。 |
| 6 | 一步一验 | 把工作切成做完就能检查的小段，绿了再往下。不要攒一批改动最后一起验。交付顺序本身要能说明问题：先看见失败，再看见修复。 |
| 7 | 只在边界上设防 | 配置、外部输入和网络在边界上校验并变成领域类型。边界里面信任这些类型，不再重复判空。业务逻辑放在能单独测试的函数里，框架外壳保持薄。 |
| 8 | 教训进结构 | 同一条叮嘱要写第二遍时，先问它能不能变成检查、类型或脚本。能变成检查的，删掉那句叮嘱。只有确实需要判断的，才留在技能或规则里，并写清失败时的样子。 |
| 9 | 用结构表达领域 | 用状态机、类型或查找表吃掉散落的分支。不要为了抽象再加一层。现有形状已经清楚、局部、不太会长大时，无聊的代码更好。 |
| 10 | 体验优先于实现方便 | 使用者包括最终用户、调用方和下一个维护者。实现方便和他们的体验冲突时，选体验。少做一个打磨过的能力，好过多做一个粗糙的开关。 |

## 和技能的关系

- `/think` 在取舍和计划里使用 1、2、9、10。
- `/check` 在审查和发布里使用 3、6、8。
- `/hunt` 在定位时使用 3、4、6。
- 测试纪律不是独立技能。只有用户明确要求，或本地测试很便宜时，才读 `skills/check/references/tdd-discipline.md`。
