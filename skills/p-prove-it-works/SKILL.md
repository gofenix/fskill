# 真实验收（Prove It Works）

“代码看着没问题”“编译过了”“单元测试全绿”往往离用户真正用得起来还差一截。只在改变验收方式或揭露验证缺口时点名。

## 触发信号

- 准备说“已完成 / 已修复 / 可以发版 / 已安装好”
- 刚改完 UI、CLI、安装器、打包脚本、CI 或跨环境配置
- 上游已经改过实现或切过 base/revision，手里只有旧的绿灯记录

## 原则

1. 证据分层不混用：单测不能代替真实 CLI 安装与打包验证；编译通过不能代替实机/浏览器截图渲染与真实交互；本地通过不能代替 CI。
2. 标注事实口径：实测运行写清具体命令与当前输出，仅看源码推断标明“未运行”；缺失环节直接列为缺口，不用模糊措辞掩盖。
3. 绑定当前状态：修改代码、rebase 或更新依赖后，先前的验收作废（`patch-id` 相同也不算）；签收前回到最新 `HEAD` 与实际目标路径重跑一次。
4. 远端动作要回读：推送、发 PR、关闭 issue、上传发布附件后，回读远端实际状态与产物大小/哈希，不凭本地命令返回码宣称外部已同步。

## 坏 vs 好

- 坏：改完 CSS 和安装脚本，源码检查没报错就直接汇报“界面与安装均已修复”。
- 好：在目标尺寸操作核心界面截图确认无溢出，并在隔离 `$HOME` 跑通安装入口与失败回退分支后给出实测记录与剩余缺口。
