# Optimize: 让指标改善经得起验证

首行内联带上 🥷，不要单独起段。

在约定预算内寻找有证据的指标改善，保留通过回归门禁的改动，交付基线、实验轨迹和最终收益；没有可测收益也是有效结论。

## 调用边界

由父技能按当前模式读取后执行，不再是独立命令。同一任务里的补充和纠正沿用这个模式。不要因为话题相近就单独启动这一节。


## 交付约定

- 目标: 用户知道哪些改动带来了可信收益、付出了什么成本，以及哪些行为和平台尚未覆盖。
- 完成条件: 本轮停止原因明确，每个已执行实验都有测量与回归结论；保留改动在最终有效版本上复核，目标未达到或证据不足时如实说明。
- 依据: 用户目标与预算、当前代码和工作区、代表性工作负载、测量入口与配置、实际运行数据、必要 profile 和回归证据。
- 交付形式: 指标与目标、基线到最终结果、保留与撤回的实验、证据路径、回归状态、停止原因及剩余缺口。

## 模式选择

| 当前任务 | 工作重点 |
|---|---|
| 开始持续改善一个已定指标 | 定好实验目标和口径，核实测量方式并跑出基线 |
| 继续已有优化或接手实验 | 重新核对历史记录、当前代码和测量条件，确认哪些结论还算数 |
| 现有数字撑不住下一轮判断 | 先校准测试负载、完成标准和噪声，先别急着叠代码改动 |

异常或回归的根因定位、一次性验证某个想法的原型实验各有分工；普通任务按原请求处理，不自动切换其他 fskill 技能。只让给建议就保持只读；已有授权就继续在范围内做实验，不用反复确认。

## 优化流程

实际委派实验或验证者前读取父技能（`hunt`）目录下的 `references/delegation-budget.md`，并保留冻结的实验预算、测量条件与操作边界。

1. **定好实验目标和口径**：读清目标入口、相关代码、项目指令和之前跑过的实验，核对当前分支、HEAD 和工作区状态（含未跟踪文件）。写明主指标、单位、优化方向、目标值、有代表性的负载、正确性和其他回归门槛、时间或资源预算以及什么时候停下。能从项目里查到的直接查，只有会改变目标或授权边界的取舍才问用户。
2. **先证明测量靠谱**：建立基线或测量条件有变时读取 [测量与证据](measurement.md)。确认指标测到的确实是完整做完目标任务的结果、输出对不对、报错能不能看出来；用有区分力的样本或小幅改动参数测一下，确认指标真的会跟着变化，不被环境噪声盖过去，再把这轮测量条件定死。记下基线波动范围和回归门槛结果，别把本来就挂的旧检查记成这轮通过。测量可重复、范围和误差都交代清楚，才算有基线可比；不然先补齐或修好测量工具。
3. **挑能证伪的假设**：进实验循环或中途接手时读取 [实验与恢复](experiments.md)。拿代码、profile 或评测失败样本讲清为什么这么改能涨、预期变化多少、什么现象说明猜错了，再做最小改动。优先选收益预期和验证成本匹配的假设，别把常见优化点排成清单瞎撞运气。
4. **单步实验并拍板**：一次只试一个假设，在同样条件下测完并跑回归门槛，再定保留、撤回还是证据不足。失败和没涨的实验也要记一笔；撤回时只回退自己这轮引入且归属清楚的改动，别动用户原有的东西。当前实验得出明确结论、代码状态干净了，再接着试下一条。
5. **复核结果并收尾**：最后在保留下来的完整改动上重新对照原始基线测一遍，顺便过一遍回归检查，别把多次试探里碰巧跑出的最高分当真实提升。达到目标、预算用完、剩下的假设收益太小，或者遇到没法安全推进的卡点时就停下，如实汇报结果；不许靠降目标、放宽门槛或藏起失败来硬凑“优化完成”。

持续优化不等于无限运行。未获跨会话调度授权时，本轮预算和宿主能力就是执行边界；恢复位置可以交付，后台调度不能凭意图自行创建。

## 硬性规则

- 指标收益以同一有效测量协议下的实际结果为准，代码阅读、单次最快值、子任务自述和只编译成功都不能证明改善。
- 冻结的测量方法或验收条件需要改变时，按测量参考重建可比基线；不能把修改判据后得到的数字拼接成旧实验收益。
- 正确性与已定回归门禁优先于主指标。无法覆盖真实生产条件、平台或工作负载时，缩小结论并说明限制，不推断普遍收益。
- 沿用项目现有 harness、工具与日志；需要可重复能力时才补最小 helper，不为套流程创建测试框架、决策系统或脚本。
- 实施、外部压测、付费评测、数据写入、委派、commit、push、PR 和调度分别遵循本任务已有授权，不因优化目标自动获得权限或扩大范围。
- 不要求固定实验次数、每轮提交、特定模型或并发规模；验证与重复投入服从噪声、风险、预算和项目要求。

## 常见误区

| 情况 | 规则 |
|---|---|
| 速度提高但完成量下降或错误变多 | 先按真实完成与正确性判定测量有效性，再讨论收益 |
| 改了 harness、数据或评分规则后数字更好 | 重跑两侧建立新基线，保留旧结论的适用范围 |
| 连续几轮没有可测收益 | 回看限制因素或失败样本，预算内换假设；收益不足时明确停止 |
| 想保留“可能有用”的改动 | 未越过噪声或门禁未通过就不计为收益，按实验参考处理代码状态 |
| 只在一个平台或微基准上通过 | 结论限于该条件，补相关端到端证据或明确缺口 |
| 评测分数提升就套性能瓶颈清单 | 按样本、评分、随机性与独立确认判断，不强找 CPU 或 I/O 限制 |

## 输出

先给“有可测收益 / 无可测差异 / 退化 / 证据不足”的结论，再简洁列出：

- **指标**：目标、单位、工作负载与测量条件，基线到最终结果及重复次数和分布。
- **实验**：保留、撤回及证据不足的假设，实际改动与轨迹位置。
- **回归**：最终版本运行过的门禁、已有失败和未覆盖的平台或行为。
- **停止**：达到目标、预算耗尽、收益不足或具体阻塞，未达目标不写成完成优化。
- **后续**：只有仍值得继续时，给最有价值的下一假设和恢复位置。
