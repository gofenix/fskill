# Hunt: 查清根因再动手

首行内联带上 🥷，不要单独起段。

## 交付约定

- 目标: 用当前证据把根因查实并做最小修复，或在指标已经定时单假设验证有可信收益；做不到时说清具体卡点。
- 完成条件: 根因或每轮假设的复现/测量前后对比、改动位置与回归验证都在本轮交代清楚；修不了或指标未达时，阻塞条件具体可复现。
- 依据: 错误日志、测试输出、trace、相关代码、最近 diff、生成物、运行状态、代表性工作负载、截图或用户复现步骤。
- 交付形式: 根因/实验结论、改动摘要、前后对比与验证结果；只让诊断或给建议就保持只读。

## 长期上下文预检

先读取 [长期上下文预检](references/durable-context.md)。可选读取，只作为背景。对 `/hunt` 来说，旧记忆可以提供历史失败模式、常见命令、既有实验口径和用户偏好的诊断边界；但当前日志、测试、代码、复现步骤、截图和运行时状态优先于旧记忆。

## 调用边界

用户显式调用 `/hunt`、`$hunt`、fskill 限定入口，或已开启的 `/f-mode` 选中时进入。已经坏了要查根因，或指标已定要逐个试假设时，也可直接选用，无需用户点名，但动手前用一句话说明按哪种问题排查及理由。

同一任务里的追问和纠正继续沿用，不用每轮重复命令。选技能只定做法，不扩大授权：只让诊断就别改文件，修复、提交和发布仍按本任务授权走。不用于代码审查（走 `/check`）、尚未定性的新功能方案（走 `/think`）或视觉审美调整（走 `/ui`）；没有故障也没有已定指标时，按普通请求处理。

指标已经定、要比较前后收益时，读取 [指标改进](references/modes/optimize/MODE.md)，一次只试一个假设。实际委派前读取 [委派预算](references/delegation-budget.md)。两个模式涉及编写或修改 TypeScript 时均遵循 [TypeScript 写法](references/typescript-style.md)（项目已有 lint 和当前文件写法优先）。

## 复现验证

改代码前，先找一个稳定、可重复、尽量窄且 Agent 能直接运行（绕不开人工观察时留日志、dump、HAR 或录屏时间戳）的复现信号，确认它直接命中用户报的原症状，而不是只证明“程序没崩”。

先弄清什么实际状态算正常、什么算坏，并确认测试的实例、版本、账号和数据就是用户报的入口。别人已经提了候选修复、commit 或 PR 时，优先验证它的效果和覆盖范围，别重复写一遍；别人认领或提交过代码，不代表自动拥有后续修改权。

没有可运行信号时，可以先用 crash dump、日志或录屏接着查，但要标明验证缺口；既没有稳定复现也没有能验证同一路径的现场采集物时，先停下向用户要环境权限、采集物或临时观测条件。

## 排查流程

1. **确认工作区与保留现场**：运行 `pwd` 或 `git rev-parse --show-toplevel` 与 `git status --short --branch -uall`，核对当前所在仓库。保留已修改、已暂存和未跟踪用户工作；未获明确授权不运行 `git switch`、`git checkout`、`git stash`、`git reset --hard`、`git clean` 或 `git worktree add`。
2. **读全报错并跑通复现**：读完用户给的日志、测试输出、截图、命令和相关文件，实跑最小命令或复查现场产物，记下修前失败证据，确认命中原症状。
3. **用证据坐实根因**：沿着输入、状态与调用链定位第一个与预期不符处，用日志、断点、临时只读检查、单测或对比结果证明根因，不凭猜测动手。
4. **最小修复**：用户要求修且根因坐实后，直接做范围内的最小修改，不反复索要同一件事的授权；只让诊断就保持只读。同一个校验守卫有多种拒绝原因时，逐条核对输入、日志和运行端能力，不漏掉并行分支。
5. **验证**：先跑复现命令，再跑相关回归测试。
   - 新增回归测试时，先在临时副本或已获准的隔离 checkout / fixture 里对修前代码实跑一次确认报红，再在修后代码上跑绿；不要为了对照去 revert 或 stash 共享工作区。
   - 如果是靠临时改代码造出的故障，先跟原始副本比对，确认改动确实落在测试会读到的代码或 fixture 上。
   - 检查否定断言（比如 `not in`）有没有假绿：配一个会触发失败的正例确认。
   - 缺陷已到达用户或已发布构建、且项目维护 `docs/incidents.md` 时，按项目台账约定补对应行。
   - 验证没过就退回排查根因，不一边报错一边扩大改动。

## 诊断参考

按问题类型只读需要的参考：

- 非显然故障模式：`references/failure-patterns.md`
- 日志、trace 产物、性能基线、缩减复现与可证伪实验：`references/logging-techniques.md`（复现成本高、变量混杂或多次修法失败时读取）
- 输入法和 Unicode 问题：`references/ime-unicode.md`
- 渲染问题定位：`references/rendering-debug.md`

## 硬性规则

- 不要在没有根因证据时修，也不要用只能证明“命令成功”的检查冒充原问题复现。
- 不要把“测试通过不了”归因于环境，除非你能证明环境差异。
- 截图证明的是事实，不是风格偏好；如果是审美问题，可建议用户显式调用 `/ui`，不自动切换技能（f-mode 开启时除外）。

## 复盘沉淀建议

修复并验证后，仅将本轮证据验证过的防复发经验列为候选；有候选时用一句话建议用户显式调用 `/retro` 或 `$retro`，没有候选时不输出也不自动沉淀。

## 输出

按问题轻重直接交代根因、改法、复现前后对比与验证结果（只诊断时交结论、证据和下一步），不硬套完整模板，也不要把“交付约定”当正文输出。需要分项展示时保持结构简洁，仅在有候选时附沉淀建议。
