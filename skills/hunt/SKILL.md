# Hunt: 查清根因再动手

首行内联带上 🥷，不要单独起段。

先证明到底为什么坏，再动手改。不要看到报错就猜修法，也不要靠连蒙带改撞大运。

## 调用边界

用户显式调用 `/hunt`、`$hunt`、fskill 限定入口，或已开启的 `/f-mode` 选中时进入。已经坏了要查根因，或指标已定要逐个试假设时，也可直接选用，无需用户点名，但动手前用一句话说明按哪种问题排查及理由。

同一任务里的追问和纠正继续沿用，不用每轮重复命令。选技能只定做法，不扩大授权：只让诊断就别改文件，修复、提交和发布仍按本任务授权走。没有故障也没有已定指标时，按普通请求处理。

## 交付约定

- 目标: 用当前证据把根因查实，再做最小改动修掉；修不了时把具体卡点说清。
- 完成条件: 复现前后对比、根因、改了哪、验证命令都在这轮交代清楚；修不了时，阻塞条件具体可复现。
- 依据: 错误日志、测试输出、trace、相关代码、最近 diff、生成物、运行状态、截图或用户给的复现步骤。
- 交付形式: 根因、改动摘要和验证结果；只让诊断就只交诊断。

指标已经定、要比较前后收益时，读取 [指标改进](references/modes/optimize/MODE.md)，一次只试一个假设。实际委派前读取 [委派预算](references/delegation-budget.md)。已经坏了、还没有选定指标时，用下文的根因流程。

## 长期上下文预检

先读取 [长期上下文预检](references/durable-context.md)。可选读取，只作为背景。对 `/hunt` 来说，旧记忆可以提供历史失败模式、常见命令和用户偏好的诊断边界；但当前日志、测试、代码、复现步骤、截图和运行时状态优先于旧记忆。

## 问题分诊

先判断问题类型：

| 症状 | 第一步 |
|---|---|
| 报错或 stack trace | 读完整错误、定位抛出点、找最近调用链 |
| 测试失败 | 跑最小失败测试，确认是断言、环境、fixture 还是生成物 |
| 回归 | 找旧好版本、最近改动、行为差异 |
| UI 截图错误 | 先判断是审美问题还是渲染/状态回归 |
| 缓存或队列异常 | 检查输入、输出、缓存 key、重试和并发边界 |

如果用户明确说“只做诊断”，不要改文件。

## 复现验证

改代码前，先找一个能稳定区分“修前坏”和“修后好”的复现信号。它必须命中用户报的原症状，不能只证明“程序没崩”或测了个旁边不相干的逻辑。优先用项目现有测试或公开命令，也可以用 CLI/HTTP 调用、浏览器脚本、trace 重放、版本对比或性能基线。

先弄清什么实际状态算正常、什么算坏，并确认测试的实例、版本、账号和数据就是用户报的入口。别人已经提了候选修复、commit 或 PR 时，优先验证它的效果和覆盖范围，别重复写一遍；别人认领或提交过代码，不代表自动拥有后续修改权。

一个好用的复现信号尽量满足：

- **准确**：走到真实出问题的路径，直接判定原症状。
- **可重复**：同样输入得出同样结论；偶现问题记下跑的次数和复现率。
- **够快**：能撑得住多轮排查；全量构建慢时，先挑最窄的入口。
- **Agent 能直接跑**：不靠肉眼盯；实在绕不开人工观察时，保留日志、dump、HAR 或录屏时间点这些可复查证据。

没有可运行信号时，可以先用 crash dump、日志或录屏接着查，但要标明验证缺口。动手改代码前，手里至少得有能稳定复现原症状的方法，或者有一份能确定走到同一路径且修后能验证的现场采集物；两样都没有就先停下，跟用户要环境权限、采集物或临时观测条件。

这里不强制 TDD、pytest 或特定测试框架，跟着目标项目的公开文档、CI 和现有测试习惯走就行。

## 排查流程

1. **确认工作区**：运行 `pwd` 或 `git rev-parse --show-toplevel`，核对当前所在仓库。
2. **读全报错信息**：读完用户给的日志、测试输出、截图、命令和相关文件，别只看最后一行。
3. **跑通复现**：实际跑一下最小命令或复查现场产物，记下修前失败的证据，确认它命中的就是原症状，别靠猜觉得旧代码肯定失败。
4. **顺藤摸瓜**：沿着输入、状态、调用链、输出走一遍，找到第一个跟预期对不上的地方。
5. **用证据坐实**：用日志、断点、临时只读检查、单测或对比结果证明根因就是这处，不是猜的。
6. **最小修复**：用户要求修且根因坐实后，直接做范围内的最小修改，不用反复问同一件事的授权；只让诊断就继续保持只读。如果同一个校验守卫有多种拒绝原因，逐条核对输入、日志和运行端能力，别只补了复现到的那一条分支。
7. **验证**：先跑复现命令，再跑相关回归测试。
   - 新增回归测试时，先在隔离的临时 checkout 或 fixture 里对修前代码实跑一次，确认它确实报红，再在修后代码上跑绿；不要为了对照去 revert 或 stash 共享工作区。
   - 如果是靠临时改代码造出的故障，先跟原始副本比对一下，确认改动确实落在测试会读到的代码或 fixture 上。
   - 检查否定断言（比如 `not in`）有没有假绿：专门配个会触发失败的正例确认一下，避免因为输出为空或者字符串根本没出现过而误判通过。
   - 验证没过就退回排查根因，别一边报错一边把改动越铺越大。

## 硬性规则

- 不要在没有根因证据时修。
- 不要用只能证明“命令成功”的检查冒充原始问题的复现验证。
- 不要把“测试通过不了”归因于环境，除非你能证明环境差异。
- 不要为了清理现场运行 `git reset --hard`、`git clean` 或丢弃用户改动。
- 不要把多个独立问题混成一个大修。
- 修复后必须跑触发问题的命令或说明为什么不能跑。
- 修复 TypeScript 时读取 [TypeScript 写法](references/typescript-style.md)。项目已有 lint 和当前文件的写法优先。
- 截图证明的是事实，不是风格偏好；如果是审美问题，可建议用户显式调用 `/ui`，不自动切换技能。

## 复盘沉淀建议

修复并验证后可以判断是否存在防复发经验，但不得自动执行 `/retro` 或发起原任务范围外的沉淀写入。

只把本轮证据验证过的经验列为候选；有候选时用一句话建议用户显式调用 `/retro`，没有候选时不额外打扰。未收到显式调用前，不为额外沉淀而修改长期上下文。落点选择由 `/retro` 负责，这里不重复。

## 输出

按问题轻重直接说清根因、改法和验证结果，简单问题不必硬套完整模板，也不要把“交付约定”当正文输出。需要分项展示时参考下面的结构：

默认输出：

```text
🥷 根因：...

修复：...

复现前后：
- `command` 或产物：修前失败 -> 修后通过

验证：
- `command`：通过/失败

沉淀建议：
- 需要时建议显式调用 `/retro` 或 `$retro`

剩余风险：...
```

只诊断时输出：

```text
🥷 诊断结论：...

证据：
- ...

下一步建议：...
```
