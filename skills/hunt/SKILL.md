# Hunt: 查清根因再动手

首行内联带上 🥷，不要单独起段。

## 交付约定

- 目标: 靠可运行复现与运行时证据定位根因，做范围最小修复或单假设指标对照。
- 完成条件: 修前失败信号、首个预期偏离点、修复位置与修后实测结果清楚交代；无法验证时直说缺口。
- 依据: 错误日志、trace、复现输出、源码与 diff、运行时状态及代表性负载。
- 交付形式: 根因结论、前后对比证据与最小改动结果；只让诊断就严格只读。

## 长期上下文预检

先读取 [长期上下文预检](references/durable-context.md)。旧记忆只作历史故障线索；当前日志、源码与复现结果优先于旧记忆。

## 调用边界

显式调用、`/f-mode` 选中，或出现明确报错、崩溃、回归、已定指标优化时进入；隐式选用前一句话说明排查目标。只诊断时绝不改文件；修、改分支与发版遵循本任务授权。代码/PR 审查用 `/check`，视觉审美问题建议改用 `/ui`，新功能规划用 `/think`。

## 排查流程

严格贯彻「先证根因」、「质疑前提」与「行为测试」：

1. **守住工作区**：运行 `pwd`（或 `git rev-parse --show-toplevel`）与 `git status --short --branch -uall` 确认位置并保护已修改/未跟踪文件；未获授权不切分支、不 `stash`/`reset`/`clean`。
2. **命中原症状的复现**：先拿到能直接触发用户原报错的窄信号（日志、测试、截图或录屏），确认测试的正是问题版本与入口，不以“命令退出码为 0”或重启掩盖问题。别人已提候选修复时，先核实其效果与覆盖，不盲目重写。
3. **追踪首个背离点**：沿调用链与关键边界加只读检查或去敏探针，区分竞争假设；连续两次修法卡在同一门槛时，按“质疑前提”停下检查共有假设。涉及输入法组合或 Unicode 字符/偏移问题时，读取 [输入法与 Unicode](references/ime-unicode.md)。
4. **最小修复与先红后绿验证**：获准修复且根因坐实后做最小改动（覆盖同一校验守卫的并行分支）。新回归测试必须在隔离副本或修前代码上先确认报红再在修后变绿；用否定断言时配正例验证；维护 `docs/incidents.md` 的项目按项目台账格式补行。修后若发现值得固化的结构规律，可按「结构防复发」落到类型、脚本或测试。

## 单假设指标改进

当指标与评估条件已明确、目标是可信收益时，先贯彻「解释数字」：固定同条件基线，**每轮只改并验证一个可证伪假设**；有可信收益且核心行为无回归再保留，否则立刻回退该改动。
