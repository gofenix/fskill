# Catchup: 把进展说清楚

首行内联带上 🥷，不要单独起段。

## 交付约定

- 目标: 用户知道上次本人消息之后发生了什么、当前卡在哪里、哪些事项需要自己处理。
- 完成条件: 相关状态已经读回或标为未核实，早先仍待用户处理的事项没有遗漏。
- 依据: 本会话、实际产物、PR 与检查状态、执行者记录；执行者的摘要只是待核对的主张。
- 交付形式: 几句平实的进展与待决事项，必要时链接现有证据。

## 调用边界

仅显式调用 `/catchup`、`$catchup`、fskill 限定入口，或已开启的 f-mode 选中时执行。直接调用无需进入 f-mode，也不改变它的开关；引用命令或讨论技能不算调用。

本次保持只读：不启动、重试、修改、批准或发布被汇报的工作，不创建持久文件。关注点只缩小汇报范围。交接给下一位 Agent 的完整现场使用 `/handoff`。

## 状态核对

以本次 catchup 前的上一条用户本人消息为变化边界，通知、工具返回与子 agent 报告不算用户消息。没有前一条消息时只报告可证实的当前状态，不编造期间变化。更早提出但仍待用户处理的事项也要保留。

只读回当前任务涉及的 PR、检查、产物与执行者状态；没有访问能力就标明未核实，不为汇报扫描整个环境。核对展示的数字，纠正先前错误时说明。不能把执行者的“完成”或旧绿灯当成当前事实。

## 汇报

先说是否有待用户决定的事项，再用几句话交代有意义的变化、仍在进行或阻塞的工作。没有变化且没有待决事项时一句话即可，不重讲用户已经知道的背景。

待用户事项限于 Agent 无法自行完成的选择、访问或批准，给推荐及理由。没有答复时，说清实际等待的部分与仍可继续的工作；沉默不授予批准，不把能自行完成的检查交回用户。

命令、hash、路径和计数只在定位或决策需要时出现，细节链接到已有产物。中文按信息量压缩，不套英文词数；必要的条件、风险和限制不能被删掉。

视觉变化优先引用已有真实截图或录像，没有就说明缺口。结构或数字用图更清楚时才绘图，不强制模板，不在图文重复同一事实，不启动应用补拍或生成虚构界面。
