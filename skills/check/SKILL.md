# Check: 交付前把关

首行内联带上 🥷，不要单独起段。

> `/review` 是 Anthropic 内置 PR 审查命令。fskill 使用 `/check` 或 `$check`，不要在本技能里重新触发 `/review`。

读取 diff，基于证据报告问题；用户已授权修复时，在授权范围内修改并验证。完成的含义是给出验证结果或明确的验证缺口。

## 交付约定

- 目标: 基于当前 diff、项目规范、文档、队列状态和现场证据，给出审查意见、技术文档核对、分诊队列、验证指南、项目审计、发版判断或发布收尾结果。
- 完成条件: 问题、修复、已交付状态或卡点都拿实际命令、产物或远端状态证明。
- 依据: 工作区状态、diff、项目公开文档、配置清单、CI、包内容、发布状态和命令输出。
- 交付形式: 先摆问题和证据；需要时再附验证结果、分诊清单、审计结论或交付状态。

## 长期上下文预检

先读取 [长期上下文预检](references/durable-context.md)。可选读取，只作为背景。对 `/check` 来说，旧记忆可以提供用户的发布习惯、审查重点和历史约束；当前 diff、工作区状态、公开文档、CI、测试、产物和远端状态优先于旧记忆。不要把旧记忆中的命令、远端状态或发布结论当成当前事实。

## 调用边界

用户显式调用 `/check`、`$check`、fskill 限定入口，或已开启的 `/f-mode` 选中时进入。任务本身属于审查与把关范围（审 diff 或 PR、审定稿技术文档、处理 issue/PR 队列、判断值不值得发版与发布收尾、做项目审计、维护验证指南、按台账做审查回归评估）时，也可直接选用，无需用户点名，但动手前用一句话说明进入哪个模式和理由。

同一任务里的追问和纠正继续沿用，不用每轮重复命令。选技能只定做法，不扩大授权：只读审查只交发现和建议，修复、commit、push、发布仍按本任务授权走。不用于尚未确定的设计取舍（走 `/think`）、根因调试或指标优化（走 `/hunt`）、或纯语言润色（走 `/write`）；日常配置与 AI 可维护性健康体检走 `/health`。

## 工作区安全预检

任何审查、交付、发布或 PR 操作前，先读取：

```bash
git status --short --branch -uall
```

把已修改、已暂存和未跟踪文件都视为用户工作。可以读取并纳入审查范围，但不能移动、隐藏、覆盖、清理或丢弃，除非用户已明确授权该操作及其范围。

默认不要运行：`git switch`、`git checkout`、`git reset --hard`、`git clean`、`git stash -u`、`git stash --include-untracked`、`git stash -a`、`git stash --all`、`git worktree add`、`git worktree remove`、`gh pr checkout`。如果确实需要换分支、另起工作区或清理，先核对该操作及范围是否已有明确授权；缺少授权时再问具体操作。在用户指定的已有分支和工作区里工作，不把“开始做”或“方案通过”当成可以新建分支或 worktree 的授权。

在脏工作区或多 agent checkout 里 commit/push 时，先记录 `git rev-parse HEAD`。commit 前、push 前都重新读取 `git status --short --branch -uall` 和 `git rev-parse HEAD`。如果 HEAD 移动、出现未知提交或工作区被别人改过，停下来报告，不要自行 rebase、recommit 或 push。

PR 检查优先用不会切换工作区的命令：`gh pr view`、`gh pr diff`、`git fetch origin pull/<n>/head:refs/tmp/pr-<n>`、`git merge-tree`。

## 模式选择

| 用户意图 | 模式 |
|---|---|
| diff 或 PR 已准备好，review、看看代码、合并前 | 默认审查 |
| 查已有 PR 状态、处理未决讨论或持续推进到就绪 | PR 跟进，按实际请求区分只读状态、讨论处理与持续推进 |
| 已成稿技术方案、PRD、spec 的正确性、一致性、完整性审查 | 技术文档审查 |
| issues/外部 PR 队列分类、补充信息重入、准备实施契约、跨多个仓库扫一遍 | 读取 [队列](references/modes/triage/MODE.md)；已有 diff 的审查仍走默认审查 |
| 建立或维护可复用的验证指南和操作入口 | 读取 [验证指南](references/modes/verify/MODE.md)。只跑一次已有测试不进入这一节 |
| 值不值得发版、is this worth a release | 发版价值判断：见下节，只判断该不该发，不执行发布 |
| commit、push、publish、release、close issue、发布表情 | 读取 [交付与发布跟进](references/maintainer-workflows.md)；查状态不附带修改或公共回复授权 |
| 打包、mac 包、dmg、notarize、apk、aab、release asset | 读取 [发布产物](references/release-artifacts.md)，并填发布检查 2.0 矩阵 |
| audit、项目代码审计、仓库质量体检 | 读取 [维护者工作流](references/maintainer-workflows.md)「项目审计模式」 |
| 只检查措辞、语法、可读性、去 AI 味或本地化文案 | 建议用户显式调用 `/write` |
| 审查提示、技能、persona 或模型变了，问审查还灵不灵 | 读取 [事故台账](references/incident-ledger.md) 的重放评估 |

每个模式前都先做项目上下文提取。普通“实施这个计划”由当前 Agent 承接，不因此进入 `/check`。

## 项目上下文提取

先从 diff 和仓库公开资料里摸清审查依据（README、AGENTS/CLAUDE、包清单、锁文件、构建和测试配置、CI、发布说明），弄明白验证命令、生成或受保护文件、发布产物、领域风险和对外回复规矩，不要依赖个人机器路径或未公开的规则。

- 项目规范和本技能冲突时，按宿主指令优先级、规则适用范围和当前授权判断，不能只因为某条写得严就推翻用户已给的授权；只澄清确实没法自行判定、又会影响动手的问题。
- 优先跑项目文档或 CI 里指定的验证命令，并看看真实 CI 工作流怎么写的。文档写了“CI 已覆盖”不算数；只在本机或只在 CI 跑过的检查，不能互相代替证明另一边也过。

上下文模板见 `references/project-context.md`。要下发版就绪判断、打包或发版前，还需要补齐发布检查 2.0 矩阵；缺证据就直说“还没验证”，不能说已就绪。如果只做 commit/push，按 `references/maintainer-workflows.md` 核对源码交付就行，不用去查无关的发版产物或包仓库。

## 默认审查

重点抓 bug、回归、漏测、生成物过期、发布风险和安全漏洞。把问题摆在最前面，按严重程度排好，每个问题给出文件行号或命令输出做依据。

1. **对齐审查基准与全量 diff**：明确要审的是本地未提交改动、PR diff 还是指定范围，冻结 `HEAD`、工作区文件清单、生成与分发面以及委派分工。
   - 算“上次发版到 `HEAD`”时，按实际发货渠道（feed、registry、应用商店或发布主机）去对齐源码 ref；不能拿另一个过期渠道的列表当基准，找不到产物和源码 ref 的对应关系就标明缺口。
   - 改动很大时，汇总各个检查视角覆盖到的路径去核对这份冻结清单（根目录文件和跨模块消费方也要算进去），只派了任务不等于真审到了。
   - 重复的语言包或生成文件，只有在确认同一项检查覆盖到每一个文件时才能合并说明；否则分开写清楚抽查了哪些、还有哪些没读。
   - 审查中途如果修过代码或仓库状态变了，旧结论作废；签收前重新核对一次 `HEAD`、工作区状态和完整 diff。
2. **顺着业务、需求与过度设计核对**：先核对改动行为是不是这次真的想要的，对照适用需求反查实现和验证证据，找出漏在 diff 外的半成品、遗漏项或超范围修改；同时逐项看新增的文件、开关、兜底逻辑和抽象层是不是真用得上，有证据证明多余的直接指出来，但别擅自替用户删掉。
3. **先报问题再决定修不修**：修改前按自动修复边界核对授权。多个问题出自同一个根因时，先判断是保留、调整、替换还是证据不足，再给局部修法；用户或项目已经敲定的方案别翻旧账重吵，审查意见也不等于授权大重构。
4. **跑验证**：跑一遍适用的验证命令，记下通过、失败或没跑成的原因。

“符合项目规范”和“做对了需求”是两码事，两头都要核对：按需求一条条查实现和测试，再从代码里查规范、回归和多余逻辑。改动复杂时可以分头委派，最后把同根因的问题按严重度合在一起，不用硬凑固定人数或固定篇幅。

diff 涉及安全前提、重复故障、视觉对比、异步完成、删减归并、安装与重试、破坏性匹配、重复计算、测试路径失真、依赖变更或验证门槛调整时，按需读取 [审查模式](references/review-patterns.md) 的对应段落；复杂独立审查的分片与裁决也在该参考。实际委派 reviewer 前读取 [委派预算](references/delegation-budget.md)，配置不授予委派权限。TypeScript 变更按需读取 [TypeScript 边界与状态检查](references/typescript.md)，沿目标项目的类型、解析与兼容约定检查。已获准编写或修改 TypeScript 时遵循 [TypeScript 写法](references/typescript-style.md)（只读审查不把风格偏好当 bug）。

涉及 CLI、安装器、配置或环境变量时，验证命令契约和真实安装路径；改过终端文案或排版后重新跑一遍命令看真实输出；修改型命令还要测失败、重试和回退边界。涉及技能、插件、包、marketplace 或生成镜像时，重建并检查产物，在隔离环境里验证安装后的入口、脚本和引用都能跑通；单测、manifest JSON 和本地导入替代不了真实安装验证，缺了哪层直接说明。

问题严重度：`P0`（破坏数据、泄露凭据、发布错误产物）、`P1`（确定缺陷、回归或安全漏洞）、`P2`（边界隐患或漏测）、`P3`（清理建议）。如果没有发现问题，明确说“未发现阻塞问题”，并说明测试覆盖和剩余风险。

## 技术文档审查

审查已经写好的技术方案、PRD、spec 或设计文档时，按文档字段、不变量、执行顺序、异常路径与现有代码/schema/测试/CI 交叉核对，只凭证据报告矛盾、遗漏和不可实现之处；只改用户授权的文档或实现。核心方案仍未确定需比较取舍时，建议改用 `/think`，不自动切换技能（f-mode 开启时除外）；仅改措辞和可读性，建议显式调用 `/write`。

## 发版价值判断

用户问“值不值得发版”“该不该发”“is this worth a release”时使用。这是判断，不是发布。

先核对三件事，再给结论：这一版实际改变了什么用户可见行为；有没有未解决的阻塞或未验证项；不发版的实际代价是什么。读当前 diff、未关闭 issue、CI 状态和上次发版以来的提交，不凭印象判断。

输出结论为**该发** / **可以等** / **不该发**，并给三条基于真实约束的理由：影响面、风险、时机。缺少发布证据时明确标为缺口，不把“看起来没问题”当成可发。

这个判断不授权执行任何发布动作。用户随后要求发布时，按交付与发布收尾和发布产物检查完成，并重新核对当时的实际状态。

## 自动修复边界

仅审查或判断是否可发布的请求，默认交付发现和建议。修法简单不代表获得修改授权。

同一任务已有明确且仍有效的修复授权时，直接完成范围内的局部 bug、文档、路径、metadata 和必要生成物修复，并运行相关验证；不因换轮或进入审查流程而重复索要批准。用户随后收窄或撤回授权时，以新边界为准。只有规范支持期望变化时才更新测试，不能为让测试变绿而改期望。

新增产品取舍、扩大重构范围、破坏性操作或外部状态变更需要各自适用的授权；发现问题本身不提供这些授权。保护无关的用户改动，遵循工作区安全预检。

## 验证

优先顺序：

1. 用户或计划指定的命令。
2. 项目文档/CI 指定的命令。
3. 根据 manifest 推导的最小相关命令。
4. 无法运行时，说明原因和建议用户运行的命令。

对脚本或 bug 修复，先用已知正确和已知错误的输入验证检查器，预期结果应来自需求而非当前实现。缺陷到达过用户或已发布构建、且项目维护事故台账时，同一个变更要补上对应行，读取 [事故台账](references/incident-ledger.md)。Agent 指令的关键词检查只能证明文本保留；行为验证要检查工具操作、产物和禁止的副作用，并在相同运行环境和输入下比较基线与候选。无法执行行为验证时明确说明，不能把文字校验通过当成行为正确。检查器或 reviewer 有变化时，同样要在相同环境和输入下比较基线与候选；对 reviewer 来说，台账里的修复前代码是已知错误集，已知干净的变更用来量噪声。

## 复盘沉淀建议

验证完成后可以判断本轮是否有值得沉淀的经验，但不得自动执行 `/retro` 或发起原任务范围外的沉淀写入。

只把本轮证据验证过的经验列为候选；有候选时用一句话建议用户显式调用 `/retro`，没有候选时不输出单独段落。未收到显式调用前，不为额外沉淀而修改 `AGENTS.md`、规则、references、ADR 或验证器。落点选择由 `/retro` 负责，这里不重复。

## 合并阻断项

- 工作区有用户改动且目标操作会覆盖它；或未经明确授权需要 force push、删除 release、关闭 issue、改 tag。
- 相关验证失败、生成物/version/package/平台 manifest/tag/release asset 不一致，或签名材料与凭据缺失、未授权覆盖已有 release asset，或有 secret/内部路径将进入公共产物。

## 输出

直接按严重度摆问题（含文件行号）、待确认假设、验证结果和必要时的复盘沉淀建议（改动摘要只作次要上下文），不要照抄“交付约定”标题或内部术语；发版判断、交付收尾、项目审计、技术文档和重放评估按各自模式约定输出对应结论与状态。
