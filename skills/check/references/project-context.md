# 项目上下文模板

`/check` 进入任何项目时，先从公开上下文提炼约束。不要把私有记忆、个人路径或机器配置当项目规则。

## 审查上下文

填这些字段：

- **审查基准**：本地 diff、staged diff、PR、range，或用户指定 commit。
- **变更范围**：语言、框架、生成物、配置、CI、发布文件。
- **验证命令**：README、Makefile、package scripts、CI 或用户给出的命令。
- **生成文件与受保护文件**：哪些文件由脚本生成，哪些不能手改。
- **领域风险**：安全、数据、性能、兼容性、用户可见行为。
- **公共回复规则**：issue/PR 回复语气和必须包含的证据。

### 按路径定的风险等级

等级由改动触及的路径决定，与大小和作者无关。一行改动落在 workflow、更新器、许可校验、安装器、提权辅助或删除路径上，就走项目最重的闸门（完整或原生测试、安全审查、维护者人工审查），且 agent、bot 或自动审查者的批准不能顶替这次人工审查。等级从项目文档里提取；项目若有按路径打印闸门的表驱动脚本，运行它并贴上输出。这类脚本只是建议不是通过：它点名的闸门可能在本会话证明不了的地方才真正执行。属于某等级的提交和 PR 还要写明如何验证、如何回退（见 `maintainer-workflows.md` 的提交步骤）。

## 发布检查 2.0

发布就绪判断、打包或发布前填适用的矩阵项；仅 commit/push 使用 `maintainer-workflows.md` 的源码交付检查，公共回复或关闭操作核对对应远端状态，不要求无关发布证据：

| 检查项 | 所需证据 |
|---|---|
| 审查基准 | 当前分支、HEAD、diff 范围 |
| 工作区 | dirty/staged/untracked 状态 |
| 远端同步 | 本地和远端是否一致，是否需要 fetch |
| 版本 | VERSION、package、manifest、tag 是否一致 |
| 生成物 | 生成物是否由官方命令重建且无 drift |
| 包与归档 | 包内容、入口文件、权限、大小 |
| 发布附件 | asset 名称、hash/size、上传状态 |
| 包注册表、appcast 与 CI | registry 最新版本、CI 状态、发布 workflow |
| 公开状态 | issue/PR/release 是否已更新并重新读取确认 |

缺少证据时，不要声称已就绪。

## 命令选择

优先级：

1. 同一任务中仍有效的用户指定命令或已确定计划中的命令。
2. 项目公开文档和 CI 命令。
3. manifest 推导的最小相关命令。
4. 如果不能运行，说明原因和可复制命令。

## 公开内容规则

- 不写入 secret、token、证书、私钥、内部路径、个人 home 目录。
- 不把一次性事故复盘直接放进公共规则；只提炼可复用原则。
- 项目案例是输入，不是通用政策。
