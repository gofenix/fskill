# Verify: 建立并养护可复用验证资产

首行内联带上 🥷，不要单独起段。

让下一位 Agent 能从项目已有入口启动正确实例、操作真实用户路径、保存证据并清理现场；交付可复跑的资产及其实际覆盖。

## 调用边界

由父技能按当前模式读取后执行，不再是独立命令。同一任务里的补充和纠正沿用这个模式。不要因为话题相近就单独启动这一节。


## 交付约定

实际委派源码核对或验证者前读取 `references/delegation-budget.md`，任务的资源隔离与操作授权仍独立成立。

- 目标: 建立或修正项目可复用的验证能力，使后续任务能通过真实表面证明行为。
- 完成条件: 建立时按资产说明完整实跑至少一项功能并确认清理后证据仍在；维护时本轮范围内的功能与入口都有源码核对和现场结果，未覆盖项与产品回归明确列为缺口。
- 依据: 当前仓库指令、公开运行文档、已有 harness、真实实例与版本、用户功能入口、操作记录、可观察结果和清理读回。
- 交付形式: 验证资产位置与运行方式、覆盖和证据、实际修正、清理结果及未满足的前置条件。

## 模式与资源

| 用户目标 | 模式 | 读取资源 |
|---|---|---|
| 缺少可复用操作入口，建立项目验证指南或 harness | 建立 | [验证资产约定](verification-assets.md) |
| 已有验证指南、功能地图或 harness，需要随产品变化保持有效 | 维护 | [验证资产约定](verification-assets.md) 与 [维护流程](maintenance.md) |

只检查配置和验证面是否健康，或只运行一次已有测试时，按相应任务处理；不因此创建一套资产。建立与维护属于同一资产的生命周期，不自动调用其他 fskill 技能。

## 建立流程

1. **确定范围与归属**：读取项目指令、当前 Git 状态与用户要求，确定要支持的表面、功能、资产目录、验证环境和可执行动作。保留 modified、staged、untracked 用户工作；仅要求分析时只交方案。
2. **发现已有能力**：从 README、manifest、Makefile、CI、测试与实际入口查明如何启动、驱动和观察。优先复用现有 harness 与项目导航，沿用用户已指定的浏览器、工具和平台边界；缺少工具或启动失败时记录具体前置，不默认安装依赖或修产品。
3. **整理验证资产**：按验证资产约定写明启动、实例诊断、操作、证据与清理，并为本轮范围建立用户功能地图。沿用项目已有验证指南或技能目录；确需项目技能时遵循目标宿主格式，保留显式调用边界，不创建常驻自动模式。只有具体重复操作需要稳定封装时才增加 helper。
4. **证明可运行**：选一项映射功能，从启动、实例诊断、真实操作到证据保存和清理完整运行；核对预期状态与副作用，再读回证据位置。失败时清理本次尝试，修资产范围内的问题后有界重试。没有完成这一轮的资产仍是草稿，其他尚未实跑的功能保持未验证。
5. **交接入口与缺口**：回读资产中的命令、路径与导航，给出后续任务可直接使用的入口、已跑功能与尚缺条件。原始运行记录保留在约定的证据位置，不把一次性报告写进长期指南。

## 硬性规则

- 这一节只建立或修正验证资产及其自有 helper。源码确认产品回归时报告证据，不改产品代码，也不把错误行为改写成期望来消除漂移。
- 本任务已有授权内的操作持续完成；安装工具、外部写入、生产验证、commit、PR 或调度自动化分别核对其适用授权，资产文件或测试环境名称本身不提供权限。
- 已有入口能完成目标时沿用，不为统一格式造通用控制器、另一套测试框架或只有转发作用的包装脚本。
- 功能地图只记录稳定用户路径、前置与可观察判据；易变实现从当前源码发现。证据的证明范围以实际运行的表面、版本、数据和入口为准。

## 常见误区

| 情况 | 处理 |
|---|---|
| 端口可连、进程存在就开始操作 | 先确认正确实例、构建与数据；具体诊断遵循验证资产约定 |
| 写完指南但没有按它跑过 | 标为草稿，给出未完成阶段与最小前置 |
| 一个入口通过就替代其余入口 | 覆盖按实际功能和入口记录，未跑项保留缺口 |
| 维护时发现应用已坏 | 区分资产漂移与产品回归，只修前者 |

## 输出

- **资产**：建立或维护模式、目录、复用与新增内容、直接运行入口。
- **覆盖**：功能与入口的源码核对、现场结果；建立模式明确本次只实跑了哪些项。
- **证据**：真实操作、预期与观察、实例和版本、可复查产物位置。
- **清理与缺口**：停止和保留的资源、清理后证据读回、未满足前置及下一步。
