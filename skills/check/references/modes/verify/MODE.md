# Verify: 建立并维护可复用的验证指南和脚本

首行内联带上 🥷，不要单独起段。

让下一个接手的 Agent 能直接从项目现有入口启动对的实例、走通真实用户操作、留好证据并清理现场；交付可重复跑通的验证指南/脚本以及这次实际测过的范围。

## 交付约定

- 目标: 把项目里能反复跑的验证指南和脚本搭起来或修顺，方便后续在真实环境里证明功能正常。
- 完成条件: 新建时至少照着说明从头到尾跑通一项功能，并确认清理现场后证据还在；维护时这轮涉及的功能和入口都对照过源码、跑出了现场结果，没测到的和发现的产品 bug 都明确标出来。
- 依据: 仓库指令、公开运行文档、现有测试脚本、真实实例和版本、用户功能入口、操作记录、实际结果以及清理后的核对输出。
- 交付形式: 验证指南或脚本的路径、怎么跑、覆盖范围和证据、实际修过的地方、清理情况、还缺的前置条件，以及维护模式的结果判定（无需修正 / 已修正 / 存在缺口）。

## 调用边界

由父技能按当前模式读取后执行，不再是独立命令。同一任务里的补充和纠正沿用这个模式。不要因为话题相近就单独启动这一节。

## 模式与资源

| 用户目标 | 模式 | 读取资源 |
|---|---|---|
| 缺少可复用操作入口，建立项目验证指南或测试脚本 | 建立 | [验证资产约定](verification-assets.md) |
| 已有验证指南、功能地图或测试脚本，需要随产品变化保持有效 | 维护 | [验证资产约定](verification-assets.md) 与 [维护流程](maintenance.md) |

只检查配置和验证入口健不健康，或者只跑一次现有测试，按对应任务直接做就行，别大动干戈新造一套指南。建立和维护都是同一个验证工具链的事，不自动切换其他 fskill 技能（f-mode 开启时除外）。实际委派源码核对或验证者前读取 `references/delegation-budget.md`，任务的资源隔离与操作授权仍独立成立。

## 建立流程

1. **定好范围和归属**：读项目指令、当前 Git 状态和用户要求，明确支持哪些端或入口、测哪些功能、文件放哪、在什么环境跑以及允许做哪些操作。留着已有的 modified、staged、untracked 改动；只让出方案就只交方案。
2. **摸清现有能力**：看 README、manifest、Makefile、CI、测试和实际启动入口，搞清楚怎么起服务、怎么操作、怎么看结果。优先复用现成的测试脚本和项目导航，沿用用户指定的浏览器、工具和平台；缺工具或起不来时记下缺少的前置条件，别擅自装依赖或直接改产品代码。
3. **写好验证指南和脚本**：按约定写清启动、实例检查、操作步骤、证据保存和清理方法，并列一份这次范围的用户功能地图。沿用项目里现有的验证指南或技能目录；确需加成项目技能时按宿主格式写、保留显式调用边界，别设成常驻自动触发。只有遇到反复要敲的固定步骤才封装小脚本。
4. **真跑一遍证明可用**：挑一个清单里的功能，从启动、检查实例、真实操作、保存证据到清理现场完整走一遍；核对预期状态和副作用，清理完再回去确认证据文件还在。失败了就清理这次试跑的现场，修好指南或脚本里的问题再有限次重试。没完整跑通的只能算草稿，其他没实跑的功能标成未验证。
5. **交接入口和缺口**：回去核对一遍文档里写的命令、路径和导航没写错，把后续能直接用的入口、已经跑通的功能和还缺的条件交出来。单次试跑的原始记录留在约定位置，别把一次性日志写进长期指南。

## 硬性规则

- 这一节只新建或修改验证指南、测试脚本和它自带的小工具。核对源码发现产品真的坏了时只报证据，别改产品代码，也别为了抹平差异把错误表现硬改写成预期结果。
- 本任务已有授权内的操作直接干完；装工具、改外部数据、动生产环境、commit、push、发 PR 或建定时任务，各自都要核对授权，指南或环境名字本身不代表授权。
- 现有入口能用就直接用，别为了凑统一格式再造一层通用控制器、另一套测试框架或只负责转发的套壳脚本。
- 功能地图只记稳定的用户路径、前置条件和肉眼/程序可判的标准；容易变的内部实现去源码里现查。证据只代表它实际跑过的端、版本、数据和入口。

## 输出

- **产物**：新建或维护了哪套指南/脚本、放哪了、复用了什么、直接怎么跑。
- **覆盖与判定**：哪些功能和入口对照过源码、哪些跑出了现场结果；新建模式标清这次只实跑了哪几项；维护模式按“无需修正 / 已修正 / 存在缺口”给出结论。
- **证据**：真实操作过程、预期和实际结果、实例和版本、证据文件位置。
- **清理与缺口**：停掉了什么、保留了什么、清理后再核对结果，以及缺的前置条件和下一步。
