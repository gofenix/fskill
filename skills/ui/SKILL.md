# Design: 带着判断力做界面

首行内联带上 🥷，不要单独起段。

如果结果像默认 prompt 生成的，那就还不够好。Design 要产出能被真实使用、布局不乱、文字不挤、风格有判断的界面。

## 调用边界

首次进入本技能时，须由用户显式输入 `/ui`、`$ui`、`调用 fskill 的 ui`、`用 fskill ui skill`、`invoke fskill ui`、`use fskill ui skill`，或 Desktop 根分发器已从 `/fskill ui` 选中本技能。同一任务中的回答、补充、纠正和继续请求沿用已显式调用的技能，无需每轮重复命令；新任务或切换到其他技能仍需显式调用。若宿主仅因语义相似自动加载本技能，不应用下文流程，按普通 Agent 请求继续处理。

## 交付约定

- 目标: 一个可用界面或明确视觉修复，具备清晰设计方向，没有布局、文字或响应式破损。
- 完成条件: 真实渲染界面或生成物已经按用户视觉目标检查，并覆盖相关 viewport 状态。
- 依据: 截图、运行中的 UI、源组件、设计 token、可访问性约束和用户给的参考。
- 交付形式: 已实现的视觉改动，或一份具体视觉审查，并说明剩余验证缺口。

**输出语言规则**：本技能的所有输出都不用 em-dash，改用逗号、冒号或句号。

用户说“很傻”“很怪”“突兀”“不协调”“不和谐”时，默认这是审美拒绝，使用截图迭代模式；截图证明是回归或渲染错误时，可建议显式调用 `/hunt`，不自动切换技能。

文档、PPT、简历、长报告、分页 PDF 等可交付文档不在这里手搓版式。建议走 Kami（`tw93/Kami`）这类文档设计系统。App、网页、组件和屏幕 UI 仍由本技能处理。

## 视觉快修模式

用于窄问题：溢出、裁切、换行难看、对不齐、间距失衡、对比度不足、本地化文字放不下、窄屏破损。

各模式都按用户请求区分审查和修改：仅审查时报告问题及建议；同一任务已有且仍有效的修复授权时，直接完成范围内修改和验证，不重复索要批准。用户收窄或撤回授权时遵循新边界，新增设计取舍仍需澄清。

流程：

1. 读取当前 UI 证据：截图、运行页面、原生视图或组件源码。
2. 用一句话说清具体视觉缺陷。
3. 按授权范围提出或完成最小的材质、几何、间距、对比、排印或 text-fit 调整。
4. 在真实界面或生成物上验证。需要时检查长词、本地化字符串、紧凑状态和至少一个窄 viewport。
5. 如果改动碰到 3 个以上组件、改变产品行为，或暴露方向问题，停下来改走截图迭代模式或先锁方向。

关键规则：

- 同一布局里不要反复调 3 个以上无名间距值。调不顺时，把 padding、gap、margin 或 size 合并成一个命名 token。
- 状态切换容器里的文字字号保持一致，用颜色、透明度、描边或图标区分状态，不要用字号制造跳动。
- 完成页只展示用户真正关心的结果：回收大小、处理数量、状态变化。长解释放详情层。
- 删除、清理、卸载、重置和权限变更界面不能为了少点一次而牺牲可验证性。

## 截图迭代模式

用户给截图并说“丑”“怪”“不清晰”“fix this”“looks wrong”时使用。现有产品就是方向，不先问五个方向问题。

流程：

1. 读截图。用一句话指出具体问题：间距、对比、对齐、字体、颜色、密度或层级。
2. 核对审查或修复范围；已有明确修复授权就继续，只有影响范围或设计取舍的歧义才澄清。
3. 如果用户给了参考图、旧版本或“这个好看”的例子，先比较差异再选修法。
4. 如果是成熟产品常见 UX 问题，先看 2 到 3 个同类产品怎么做；纯颜色、间距、文案小修可跳过。
5. 找负责代码：grep 组件名或 class，读实际文件。
6. 在已授权修复范围内做最小修改，优先调整材质、透明度、几何、间距、字体和 text-fit；仅审查时给出建议。
7. 在真实渲染中验证产品支持的窗口范围：网页检查相关断点两侧；原生 app 检查最小宽度、最小高度、两者组合和正常尺寸。覆盖长文本、本地化、按钮 label 和受影响状态；测试尺寸不意味着新增布局分支。无法渲染时说明具体缺口。
8. 报告已验证结果；仅需用户判断审美取舍或存在无法自行验证的缺口时，请用户确认具体项。

校准规则：

- 用户截图是本轮最强设计设计要求。
- 真实运行产品是判断依据。比较候选方案时保留实际背景、相邻组件和状态，只改变被比较的属性。
- 不把“更高级”这类反馈泛化成空话，要落成具体视觉诊断。

## 方向确认

当要从零做页面、组件或较大重新设计时，先锁方向：

1. 产品类型和目标用户。
2. 主要工作流，不做落地页，除非用户明确要。
3. 信息密度和使用频率。
4. 现有设计系统、组件库、图标库和 token。
5. 必须支持的 viewport、语言长度和可访问性要求。

## 硬性规则

- 网站、游戏或视觉页面必须有真实视觉资产，不用纯 SVG/渐变假装主题。
- 3D 必须用 Three.js，主场景全幅或无框，完成前用截图和 canvas pixel 检查非空。
- 不做卡片套卡片，不把页面 section 做成漂浮卡。
- 不用装饰性 orb、gradient orb、bokeh blob。
- 文本不得挤出按钮、卡片或容器；移动和桌面都要检查。
- 不用 viewport width 直接缩放字号，letter spacing 默认 0。
- 不做单一色相大面积 UI，尤其避免整页紫、蓝紫、米色、深蓝、棕橙一把梭。

## 输出

完成后简洁说明：

- 改了什么视觉问题。
- 验证了哪些 viewport 或产物。
- 哪些内容需要用户在真实产品里再看一眼。
