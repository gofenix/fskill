# 现有产品优化

fskill 改写说明：保留既有快修与截图迭代边界，将上游评审、打磨和边界状态方法重组为按问题影响选择的工作流。来源与许可统一见仓库根目录的 `LICENSE`。

现有产品就是设计证据。缺少 `DESIGN.md` 不构成重设计理由；局部打磨沿用已有视觉语言、事实文案、功能与平台惯例。

## 无基线的改进

读取运行页面、用户截图／参考、负责组件、token 与相关状态。保留与问题有关的改前证据和核心任务路径；只有截图时先做可见范围的诊断，不把无法看到的交互推断成事实。

比较候选方案或改前改后时使用相同数据、屏幕尺寸、背景、相邻组件和状态。用户参考表达审美目标，当前运行结果和源码用于核实实现。出现冲突时先说明差异与证据的新旧。

## 混在一起的评审

按请求与问题选择评审维度，不为小修执行全部项目：

| 维度 | 需要回答的问题 | 证据与交付 |
|---|---|---|
| 体验与视觉评审 | 任务能否完成，入口、层级、密度与文案是否清楚 | 指出具体位置、用户影响与建议，区分观察和推测 |
| 技术质量检查 | 键盘、焦点、对比度、响应式、溢出或性能是否有缺陷 | 使用项目可用检查工具与实际操作，记录检查范围和未覆盖项 |
| 收尾打磨 | 对齐、间距、排印、图标、状态切换是否一致 | 保留上下文做局部修正，优先复用公共 token 与组件 |
| 边界状态 | 长文本、本地化、空、加载、错误、禁用或失败恢复是否成立 | 触发与改动相关的真实状态，不只检查理想数据 |

自动检查只能证明它检测的项目，不能代替体验和视觉判断。这里是 `/ui` 内部方法，不新增独立子命令，也不假设安装了上游检测器或浏览器插件。

## 按审美偏好排序

先处理阻断任务、不可访问、信息丢失或误操作风险，再处理层级、效率与一致性，最后打磨装饰细节。相同影响下优先选择范围小、可复用的修正，不机械地先换字体或配色。

把“更高级”“很怪”落成具体诊断，例如“主操作与次要动作同权”“状态切换造成布局跳动”。较大 UX 问题可对照少量同类产品的相关流程；纯颜色、间距、文案小修无需额外调研。

仅评审时交付按影响排序的问题、依据和可执行建议，不改项目。修复已获授权时直接完成范围内改动；碰到新行为、事实文案变化或整体方向取舍时重新界定范围，不将打磨扩成改版。

## 快修扩大成重设计

溢出、裁切、换行、对齐、间距或窄屏破损，先用一句话描述缺陷，找到实际组件，完成最小修正后检查受影响状态。发现问题跨多个组件、改变产品行为或暴露方向冲突时，改用整体诊断或明确改版范围。

同类间距与尺寸反复调不顺时用命名 token 收拢；状态切换通过字重、颜色、透明度或图标表达，不靠字号改变造成跳动。完成页先展示用户关心的结果，长解释进入详情。删除、清理、卸载、重置和权限变更不能为少点一次牺牲可验证性。

## 截图好看但问题仍在

按入口的真实验收操作受影响流程，结合相同条件的前后截图说明问题如何改善。涉及动效时检查连续过程，静态截图无法证明跟手与可中断性。没有测量的效率提升不写成已验证结论。

用户明确要求整体改版时，保留产品事实、功能和平台约束，使用新产品参考提出替换视觉方向；原有外观此时是基线和待改善证据，不能反过来阻止已授权的方向变化。
