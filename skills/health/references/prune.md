# 规则瘦身模式

用户要求精简、瘦身、裁剪 agent 指引时读取：全局规则、用户或项目 skill、`AGENTS.md` / `CLAUDE.md`、路径规则、记忆索引。目标是每次会话少占上下文，同时不丢约束、不丢能力。两者冲突时，优先级是：保住约束 > 放对层 > 减少字数。大部分冗余是"在错误的时机加载"，不是"本就不该存在"。

## 交付物

- 一份台账，每行一个段落或一组行：`file:line`、动作（`fix`、`delete`、`move`、`edit`、`keep`）、move 的目标位置、理由。无法验证的用量、无法测试的行为和超出范围的表面另列缺口清单。
- 瘦身前后的常驻体积：用收集器 `STARTUP CONTEXT ESTIMATE`（`local_agents_*`、`local_claude_*`、`rules_*`、`skill_desc_*`）和 `PATH-SCOPED CONTEXT`，加上记忆索引。项目级瘦身时，`global:` 规则和机器级 skill 各报一次为范围外，不进台账。
- 用户确认台账前只报告，不改文件。修复阶段只执行已确认的行，结束时跑「搬运与验证」下的检查。

## 盘点

- 区分每次会话都加载的和按需加载的。常驻的文件比更大但很少加载的文件更贵。
- 判断 skill 有没有人用要看真实调用记录，不能 grep 名字：注入的技能清单里每个名字都在。刚装好、零调用不等于没人用。没有记录是缺口，不是证据。

## 逐段判断

- `fix` 优先，风险最低：引用了已不存在的文件、命令或选项，两段互相矛盾，自己声明过时的行，供应商已改变的工具用法。对照当前代码和官方文档核实，不凭记忆。
- `delete` 的条件是删掉不改变行为：一个够用的模型本来就会遵守的默认做法（改前先读、改完跑测试、处理边界情况）。描述性句子常常内嵌约束（"绝不写入 `~/.config`"、"不上传用户内容"、"失败时保持安静"）：描述可以删，分句要留，因为代码说明它做了什么，不说明它绝不能做什么。整段要逐句判断：保住一个陷阱，不等于可以连带丢掉旁边的许可或安全分句。
- 限制 agent 能碰什么、能打包什么的规则不算默认做法，写得再通用也不算：改动仓库外的文件要先展示并确认，用户可见的改动（UI、配置字段、默认值、权限）不搭清理补丁的车。拿不准就保留，或者对比一次不带这条指引的干净会话。一步问答只能证明知道，不能证明长会话里还记得；任务永远不会触发的探针也不是证据。
- `keep` 的是模型猜不到的：用户偏好、被否决的方案及原因、产品取舍、机器与环境事实、静默陷阱（退出码 0 但结果为空或错误，或看起来像故障的正常行为，比如首次构建要十分钟）。报错明确的显性陷阱不需要常驻规则，最多在报错处留一句提示。
- 单向门永不压缩：删改用户数据、金钱、发布、提权、重写已推送历史。整段搬运且措辞不动，或者保留。
- 留原因，去故事。"因为这会丢数据"留下；事故经过、日期、来源文章的篇幅去掉。带日期的维护者标记（`(维护者 2026-11-08)`）或决策编号（`D281`）是规则所依赖的权威依据，不是故事，要留。一次性的报告、评分卡或诊断快照是证据：提炼出稳定规则，然后丢掉报告。

## 判断落点

| 内容 | 层 |
|---|---|
| 跨项目的硬约束 | 全局规则 |
| 需要判断或追问的可复用流程 | skill |
| 项目命令、路径、发版步骤 | 项目指引 |
| 同输入同输出：查询、状态、校验 | 脚本或 hook |

- 低层复述高层，只对"确实加载高层"的运行时才算 `delete`；Cursor 或其他从不读全局文件的运行时也在该项目里工作时，重复全局规则的项目规则要留。同一事实存在多处时，从单一来源生成，或只留一处。
- 一句话同时出现在对外表面（站点页面、README、包描述、技能的生成副本）时，它是对外文案而非指引：grep 整棵树，生成镜像也算，措辞交给用户定。
- 一个项目只留一份指引。Claude Code 里根 `CLAUDE.md` 会让项目关掉 `AGENTS.md`（含嵌套指引）；需要 Claude 专属行时，用以 `@AGENTS.md` 开头的 `CLAUDE.md`。这随版本变化，用下面的加载探针确认。
- 根文件保留"一次对话不读任何文件就能触发"的内容（提交、发布、回复、删除），因为路径规则只在读到匹配文件时才加载。发版时红线与入口留在根，参数跟着脚本走。
- move 的目标必须能独立加载：路径规则，或嵌套 `AGENTS.md`（Claude Code 在没有根 `CLAUDE.md` 时、Codex 和 Cursor 始终会读）。`docs/` 下的文件只在 agent 打开时才加载，搬到那里等于要留一行根指引说明何时去读。
- 带 `paths:` 的 `.claude/rules` 只到得了 Claude Code。项目里还有读 `AGENTS.md` 的 Codex、Cursor 或其他运行时，必须遵守的规则要留在根 `AGENTS.md` 或嵌套 `AGENTS.md`；嵌套指引若位于部署或打包目录，要随包一起发。
- skill 正文承载每次运行都要的内容。互斥的模式和只有部分运行需要的细节移到 `references/`，由一行点名触发条件。description 说清做什么、何时用、`不用于`；近义词清单和多语言触发词留在外面，因为每次会话都在为它付费。

## 改写留下的内容

- 面向结果而非路线：结果、完成标准、证据、输出。删掉后模型还能用别的方式达成同样结果的步骤属于路线；顺序本身就是约束的步骤要留（发布前验证、删除前确认）。
- 同一质量要求写三遍，收敛成一个模型本来就在用的引导词。
- 用 NO/OK 对照点名坏味道，而不是写"要做到 X"。新的目录行并入它所例示的原则；一个概念只用一个名字。
- "做 Y 之前读 X"这种文本指令执行不可靠；改成在 Y 发生时注入 X 的 hook。注入的上下文可以随工具结果一起到达，所以不可逆动作在第一次尝试时就应被拒绝，并说明原因。

## 搬运与验证

- 先搬再压。改写正是约束在机械检查全绿时丢失的地方；整行搬运能保住措辞。
- 修复后在项目根运行 `python3 <skill-base-dir>/scripts/check_moved_lines.py <base-rev>`（目标在默认指引路径外时用 `--include GLOB`）。每一条缺失行都必须对应台账里已确认的 `delete` 或 `edit`。
- 重跑收集器：`path_rules_matching_nothing` 必须为 0；每个会删除、搬运或上传用户数据的源文件，仍必须命中管辖它的规则，出现在 `largest_effective_paths` 或直接选择器校验里。
- 拆分后 grep 旧文件名：仍把读者指向旧位置的指针会静默过期。
- 瘦身提交后做过删审计：用 `check_moved_lines.py <base-rev> --head <prune-rev>` 列出消失的行（每个瘦身提交跑一次），只把这份清单和仓库交给没参与瘦身的审查者。审查者对每条丢失行 grep 关键词而非整句，只有在当前树中任何位置都找不到该含义时才标记，标记的行从基线版本原样恢复。
- 新增或移动的文件要对照发布范围检查：部署目录、包的 `files`、打包白名单。
- 加载探针会启动会话，需要授权：在被移动的文件里放一行哨兵，读一个匹配文件后开新会话问它，再读一个不匹配的文件后问一次。然后跑一个真实任务和规则本来要防的历史故障，把 diff 交给没参与的人审查。
