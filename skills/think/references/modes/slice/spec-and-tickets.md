# 规格与票据

在需要把已定讨论固化为规格、创建逐票契约或规划机械迁移时读取。沿用项目现有格式，以下字段是内容要求，不要求改造 tracker。

## 已定讨论固化

把已有决定综合成规格，不重新访谈，也不为覆盖率填大量重复 user stories：

```markdown
# <功能规格>

## 问题与目标
谁在什么场景遇到什么问题；完成后能观察到什么变化。

## 已确定行为
- 正常路径、关键异常和兼容要求；每项可追溯到当前讨论或规格依据。

## 已定约束与接口
- 模块职责、领域术语、公开接口、schema 或状态转换；记录决定的原因。

## 验证边界
- 从哪个现有公开入口观察行为、覆盖什么、未覆盖什么；已有同类测试指针。

## 范围外
- 明确不包含的行为与迁移。

## 最小未决阻塞
- 仅列会改变范围、依赖或验收的缺口；没有则写“无”。
```

已有确认的测试边界直接沿用。没有明确边界时，优先选择能观察目标行为的现有公开接口，说明能发现和不能发现的问题；如果边界选择关系到产品行为或重大测试成本，再做最小澄清。不要为所有小改动强制新增测试或要求用户逐个批准测试入口。

通常用稳定接口与行为描述实现决定。类型、schema 或状态机片段比文字更精确时保留决定所需的最小片段，不复制整份原型。

## 每票契约

```markdown
# <ID>: <交付标题>

Source: <规格或父票指针>
Status: pending
Blocked by: <ID 列表，或 none>

## Scope
本票交付的完整行为；明确不包含的相邻工作。

## Acceptance
- [ ] 给定 <输入/前提>，从 <公开入口> 可观察到 <预期结果>。
- [ ] 关键异常或兼容条件。

## Verification
- 适用命令或演示步骤、独立的预期结果、必要环境及剩余验证限制。
- 已定测试边界与现有测试指针；不把实现内部调用次数当成行为验收。

## Parallel ownership
- 可能修改的模块/当前文件线索、共享文件风险、由谁负责合入共享改动。

## Interface clues
- 依赖和提供的稳定接口、输入输出、兼容承诺；未知项是否阻塞开工。
```

不要让验收标准重算实现逻辑后宣称相等。测试的预期值来自规格、已知样例或独立规则；测试、演示、类型检查和平台运行分别证明什么，要写清楚。

没有代码变动的准备票也要可验收，例如“新增兼容入口后旧调用与新调用都可运行”；“完成预整理”“搭好基础”不足以验收。

## 任务图与 tracker

一个任务图保留规格指针、批准状态、ID 到票的映射和 `blocked_by` 列表。先建 blocker，再建下游票；有原生 blocking 关系时沿用，没有时在正文写清楚，不把平台关闭状态直接当成实施验证证据。

本地没有既有约定时：

```text
.scratch/<feature>/
  spec.md
  graph.md
  issues/
    01-<slug>.md
    02-<slug>.md
```

每张票单独保存，编号稳定且不因重排而重用。`graph.md` 写清来源、批准范围、blocking 边、可开始的票和并行 ownership。实施阶段可以附加机器可读状态账本，票据仍是行为契约的来源。

外部 tracker 的票号与本地 ID 保持显式映射。发布到一半失败时先读回已创建的票和边，再补缺失项；不从头重建导致重复票，不关闭或覆盖未知父票。用户只要草案时，不进行外部写入。

## Expand–contract

机械修改影响许多调用方时，不把 schema、接口和调用方一次性破坏掉：

| 阶段 | 交付与验收 | Blocking |
|---|---|---|
| Expand | 新形式与旧形式并存，已有行为继续工作，新入口可验证 | 原规格要求的真实前置 |
| Migrate | 按模块/影响范围迁移一批调用方，混用时仍兼容，每批独立通过适用验证 | Expand；仅依赖实际需要先迁移的其他批次 |
| Contract | 证明旧调用方已经归零，删除旧形式与过渡路径，最终行为通过验证 | 所有相关 Migrate 票 |

先确认可观察的兼容条件，例如旧数据与新数据、旧客户端与新服务是否需要共存。把过渡期行为也写进验收，而不是只检查最终新接口。

一批无法独立通过验证时，先调整兼容层或粒度；实在不能分开的变更放在同一张可验收票里，缩短中间不稳定状态。每张票的 blocking 和完成证据必须真实，不能把未验证的中间票标为完成来解锁最终集成。
