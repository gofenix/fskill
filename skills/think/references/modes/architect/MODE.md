# Architect: 找到值得改进的代码边界

首行内联带上 🥷，不要单独起段。

从真实维护摩擦出发，找出值得保留或调整的模块边界；说明改前改后如何影响调用方、变化集中度和测试，并给出有证据的推荐。

## 调用边界

由父技能按当前模式读取后执行，不再是独立命令。同一任务里的补充和纠正沿用这个模式。不要因为话题相近就单独启动这一节。


## 交付约定

- 目标: 用户知道哪里存在值得处理的架构摩擦、哪里应保持现状，以及最值得采取的边界改进是什么。
- 完成条件: 推荐有真实调用和变更或测试证据，说明改前改后、备选取舍与验证范围；没有足够收益时明确建议保持，不为了产出强造候选。
- 依据: 用户方向、项目领域文档与 ADR、实际调用路径、相关 git 历史、当前代码与测试，以及已授权实施的边界。
- 交付形式: 按收益和证据排序的精简候选、优先推荐与限制；已选边界可交付接口比较，获准落地时附实际改动和验证。

## 模式选择

| 用户当前目标 | 工作重点 |
|---|---|
| 找出哪里值得改善架构 | 限定范围，检查调用、热点、认知成本和测试摩擦 |
| 深入已选候选 | 比较接口、隐藏的复杂度、依赖和测试接缝 |
| 已授权实施所选边界或约束 | 最小落地并验证行为与边界检查 |
| 只要求架构诊断 | 只读分析，交付证据与建议 |

它回答“什么边界值得改善”。既成 diff 的正确性和项目风险审查、既定需求的普通方案各有范围，这一节不自动切换其他 fskill 技能。

## 识别候选

1. **先定扫描方向**：用户指定模块或痛点时沿用；否则结合相关 git 历史找反复修改的区域。没有明显热点时再扩大，历史不足时说明，不能把缺少历史当成没有问题。
2. **读取现有约束**：沿用项目领域名称、公开架构文档与 ADR，确认模块职责、调用者和已有刻意取舍；先理解原因，再判断是否值得重开。
3. **追踪维护摩擦**：选择真实行为沿调用链阅读，找出理解一个概念需跳转多处、调用方重复知道内部规则、薄转发层、共享状态泄漏，以及难以通过当前接口验证的行为。
4. **检验边界价值**：读取 [references/module-design.md](module-design.md)，按调用方必须知道的全部信息评估接口，用假想删除检验复杂度究竟消失还是转移。文件多、小函数多或实现行数多，本身不是问题证据。
5. **形成候选**：每项给出具体位置和痛点、改前改后结构、保持或调整的备选、调用方收益、测试影响、迁移成本、推荐强度与未知项。可推荐保持、拆分、合并或深化，不预设“大模块总更好”。
6. **推荐并收束**：优先推荐有实际使用与变化证据、收益超过成本的方案。用户仅要求扫描时止于候选；全部候选只是猜测时说明未发现足够依据，不扩展成无尽设计访谈。

## 深入与落地

选定候选后，明确它应隐藏的复杂度、现有消费者、必须保持的行为及变化来源。表示与所有权、依赖分类、备选接口的独立比较与融合，以及迁移和重新设计的条件，沿用 [references/module-design.md](module-design.md)；比较接口与真实调用示例即可，不硬造多份实现。

只读分析或选中候选都不自动授权修改代码。用户已授权实施时，沿所选边界做最小改动；需要把已经确定的访问约束落成执行检查时，读取 [references/boundary-enforcement.md](boundary-enforcement.md)。它适用于项目已有语言与工具，不强制 TypeScript、固定目录或 dependency-cruiser。

## 硬性规则

- 接口包含类型签名之外的语义、调用顺序、错误、配置、不变量与性能承诺；物理上禁止深层 import 不能证明接口已经隐藏复杂度。
- 候选必须说明复杂度由谁承担，变化和验证集中在哪里；“更干净”“更符合模式”不能代替收益证据。
- 接缝来自实际变化、测试替身或外部依赖；不为假想扩展制造抽象，也不为证明有接缝伪造第二个 adapter。
- 已有 ADR 只在真实摩擦足以挑战原理由时重开，明确冲突与新证据；是否形成新 ADR 沿用项目约定和本任务授权。
- 旧测试只有在等价行为覆盖已确认且不再提供独立价值时才考虑删除；保留有意义的内部验证，不机械清空单元测试。
- 默认用文字、表格和必要的小图解释；不强制 HTML、Tailwind、CDN 或宽松安全配置。实际创建可视产物时遵循用户请求与宿主能力。

## 常见误区

| 情况 | 规则 |
|---|---|
| 一个函数只有几行 | 追踪它承载的语义与调用方知识，不按行数判浅 |
| 提取了更多文件，测试更容易 mock | 检查真实行为是否更集中，避免测试只验证分散的转发 |
| 入口文件禁止绕过了 | 还要核对调用方是否仍知道内部顺序和不变量 |
| 只有维护者不喜欢目录结构 | 给具体行为或变更证据；否则建议保持 |
| 所有方案都差不多 | 回到真实消费者与约束，不为了“design it twice”制造假差异 |
| 用户说“就选这个” | 区分选择设计与授权实施，沿已有任务授权继续 |

## 输出

先给推荐或保持结论，再列有依据的候选及其改前改后、取舍、测试收益与风险；标明哪些是观察、哪些仍需验证。深入候选时交付接口对比与真实调用示例；已实施时报告实际变更、必要验证和剩余缺口。分析完成且未发现问题时回复“✅OK”；有范围或验证限制时简短说明。
