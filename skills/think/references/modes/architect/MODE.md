# Architect: 找到值得改进的代码边界

首行内联带上 🥷，不要单独起段。

从平时改代码最费劲的地方出发，找出哪些模块边界值得调整、哪些保持现状更好；讲清楚改前改后对调用方、改动集中度和测试的影响，再给出有依据的建议。

## 交付约定

- 目标: 让用户搞清楚哪里真的有值得改的架构痛点、哪里不用动，以及最划算的边界调整是什么。
- 完成条件: 每条建议都有真实调用链路和历史变更/测试证据，说清改前改后对比、备选取舍和验证范围；收益不够时直说保持现状，别硬凑候选。
- 依据: 用户目标、项目领域文档和 ADR、实际调用路径、相关 git 历史、当前代码与测试，以及已授权落地的范围。
- 交付形式: 按收益和证据排好序的精简候选、主推荐和限制；选定某项后可做接口对比，获准修改时附实际改动和验证。

## 调用边界

由父技能按当前模式读取后执行，不再是独立命令。同一任务里的补充和纠正沿用这个模式。不要因为话题相近就单独启动这一节。

## 模式选择

| 用户当前目标 | 工作重点 |
|---|---|
| 找出哪里值得改善架构 | 限定范围，看真实调用、变更热点、调用方负担和测试痛点 |
| 深入已选候选 | 比较接口写法、收进内部的复杂度、依赖关系和可替换测试边界 |
| 已授权实施所选边界或约束 | 最小改动落地，并验证行为和边界检查 |
| 只要求架构诊断 | 只读分析，交出证据和建议 |

它回答“什么边界值得改”。审既成 diff 有没有 bug、或拿定需求出普通实现方案各有归属，这一节不自动切换其他 fskill 技能（f-mode 开启时除外）。

## 识别候选

1. **先定扫描方向**：用户指定了模块或痛点就按指定的来；没指定就先翻 git 历史，找老是一起改、反复改的地方。没有明显热点再扩大范围，历史太短时直说，别把没历史当成没问题。
2. **读清原有约束**：沿用项目的业务词、公开架构文档和 ADR，看清模块原本的职责、调用方和当年特意做的取舍；先弄懂为什么长这样，再谈值不值得重改。
3. **顺藤摸瓜找痛点**：挑真实业务流顺着调用链读一遍，抓这几类问题：看懂一个概念要跳好几个文件、调用方反复在替被调方操心内部规则、只有一层薄转发、共享状态漏得到处都是，或者通过现有接口根本测不到核心行为。
4. **掂量边界值不值得调**：读 [模块、接口与测试接缝](module-design.md)，按调用方必须知道的全部细节来评估接口，用“假设删掉这层”试试看复杂度到底是真消掉了，还是只是换了个地方藏着。文件多、小函数多或行数多，本身不算坏架构证据。
5. **整理候选**：每项写明出在哪、痛在哪、改前改后结构、保持还是调整的备选、调用方省了什么心、测试好改多少、迁移成本、推荐强度和未知项。可以建议保持、拆分、合并，或者把细节收进模块内部，别预设“大模块一定更好”。
6. **挑出最值得做的并收口**：优先推有真实使用和变更证据、收益大过成本的方案。只让扫描就止步于候选列表；如果全都是猜测，直说证据不够，别拉着用户展开漫无边际的设计访谈。

## 深入与落地

选定候选后，明确它该把哪些复杂度藏在内部、有哪些调用方、哪些行为不能变，以及未来主要会因为什么而改。内部表达与归属、依赖怎么分类、备选接口怎么分开对比和融合，以及何时需要迁移或重设计，继续看 [模块、接口与测试接缝](module-design.md)；比较接口签名和真实调用示例就够了，别硬写好几份完整实现。

只读分析或选中候选都不代表授权改代码。用户确实授权动工时，沿选定边界做最小改动；要把已经定好的模块访问约束做成自动检查时，读 [把已选边界落成可执行检查](boundary-enforcement.md)。这套检查跟着项目现有语言和工具走，不强推 TypeScript、固定目录或 dependency-cruiser。

## 硬性规则

- 接口不只是类型签名，还包括背后的语义、调用顺序、错误约定、配置、不变量和性能承诺；光靠 lint 禁止跨层 import，不代表接口就已经把复杂度包住了。
- 提候选必须说清复杂度最后由谁扛着、改代码和测试会集中到哪；“看着更干净”“更符合某某模式”不能算收益证据。
- 可替换边界（接缝）必须对应真实会变的需求、测试替身或外部依赖；别为假想的以后扩展提前加抽象，也别为了凑出“我设计了两个实现”硬写假 adapter。
- 只有现实痛点真的足以推翻当年理由时才重开旧 ADR，写清哪里冲突、新证据是什么；要不要写新 ADR 看项目约定和这轮授权。
- 旧测试只有确认已有等价行为覆盖、且不再提供额外价值时才考虑删；有意义的内部校验照留，别机械清空单测。
- 默认用文字、表格和必要的小图讲清；别强上 HTML、Tailwind、CDN 或放宽安全配置。确实要画可视产物时看用户要求和宿主支持。

## 常见误区

| 情况 | 规则 |
|---|---|
| 一个函数只有几行 | 看它承载了什么业务语义、逼着调用方知道多少细节，不按行数判浅 |
| 拆出更多文件，测试更容易 mock | 看看真实行为是不是反而散了，别让测试只测一堆无意义的转发 |
| 入口文件已经禁止绕过了 | 还要核对调用方是不是依然得记住内部调用顺序和不变量 |
| 只是看着目录结构不顺眼 | 拿出具体行为或变更历史证据，拿不出就建议保持现状 |
| 几个方案其实差不多 | 回到真实调用方和硬约束再看，别为了“design it twice”硬捏假差异 |
| 用户说“就选这个” | 分清“选定方案”和“授权改代码”，按当前任务授权推进 |

## 输出

先给推荐调整还是保持现状的结论，再列有依据的候选以及改前改后对比、取舍、测试收益和风险；标清楚哪些是实锤观察、哪些还要再查。深入分析时给出接口对比和真实调用示例；已经落地的，报告实际改动、必要验证和剩下的缺口。分析完没发现值得调整的架构问题时，明确说明“未发现需要调整的边界问题”，并补一句已查范围和扫描限制。
