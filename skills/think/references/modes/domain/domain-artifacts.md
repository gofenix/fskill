# 领域内容的落点与确认

在选择术语文件、厘清多上下文或记录已定决策时读取。项目已有约定优先于下面的缺省格式。

## 先沿导航找落点

1. 读取当前仓库指令、README 和相关模块导航，寻找 `CONCEPTS.md`、`CONTEXT.md`、`GLOSSARY.md` 或等价文件及 ADR。
2. 存在多个候选时，优先使用已被导航指向且覆盖当前业务语境的文件；不是简单按文件名胜出。相互冲突且无权威入口时，给出冲突后确认落点。
3. 若已有 `GLOSSARY-MAP.md`、context map 或模块级术语导航，先找到当前 bounded context，再读取对应定义和关系。不为一次澄清新造一套平行映射。
4. 没有现有约定时，可建议根目录 `CONCEPTS.md`；只有存在已确认内容且有写入授权时才创建，并补最小导航。

一个概念只维护一个主要定义位置。导航链接帮助发现，不复制整段词义。

## 定义只保存确认后的领域事实

沿用原格式；无格式时可用：

```markdown
## Ordering
接收并跟踪订单的业务语境。

**Order**: 客户提交并由 Ordering 跟踪履约状态的一次订购。
避免混用: Invoice、Payment。
```

定义通常一到两句；只列真正会造成混淆的别名，不把所有同义词都禁用。定义回答“它是什么以及如何与相邻概念区分”，事件或状态的细节按项目已有领域文档承载，避免术语文件膨胀成规格。

长期术语文件不保存一般编程概念、临时假设、实现方案、会话记录或尚未确认的业务期望。新定义得到确认后，在已授权范围内就地更新；存在同义条目时合并，不追加另一种编码。

## 跨上下文的同名词

把名称与语境一起理解。例如 Ordering 的 Customer 可能是下单主体，Billing 的 Customer 可能是付款账户；二者不必一一对应，也不必强制改成同一个对象。

需要核对的是：

- 谁拥有该概念和状态，谁只能引用或接收投影。
- 交互传递的是 ID、快照、命令还是已发生事件。
- 翻译发生在哪里，是否丢失或新增了语义。
- 哪个行为或反例能区分两个概念。

这些关系沿用现有 context map 或领域文档；术语定义保持简短。只有边界选择已经确定且满足 ADR 门槛时，才进入决策记录。

## 用证据处理冲突

记录三个层次：用户说法、文档定义、当前代码与测试表现。列出具体路径或引用，并展示至少一个会产生不同结果的情境。不要把测试通过当成词义已获业务确认；也不要因用户提出新要求就把当前实现描述成已变更。

有相关公开决策记录或用户提供的票据时，按需核对，避免重新争论已知取舍；不搜索无关历史或私有材料来补造权威。

## ADR 的最小落点

仅对同时难以逆转、缺少背景会令人困惑且经过真实取舍的已定决策使用。沿用现有目录、编号与模板；没有约定时建议 `docs/adr/NNNN-slug.md`，读取最大编号后递增，避免覆盖已有记录。

```markdown
# 决策标题

一到三句话说明背景、已决定做什么、为何选择它。
```

只有会影响后来判断的被拒方案和后果才补充。尚未决定的方案保留在当前讨论或已有 proposal 中，不伪装成 accepted ADR；更改既有决策时保留替代关系与原因。
