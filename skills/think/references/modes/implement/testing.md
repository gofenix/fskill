# 行为验证

用户要求 test-first、风险需要回归测试或现有测试需要扩展时读取。验证投入跟随失败风险、项目要求与票据验收；文案、机械改名或低影响可逆改动不默认新增测试。

## 选择观察入口

沿用规格已定或项目已有的公开测试边界，例如请求入口、模块公开 API、命令行输入输出或 UI 可观察行为。优先选能覆盖目标行为的现有边界，说明能抓住和抓不住的问题；不会改变 scope 的常规测试选择无需逐项向用户确认。

边界本身会改变产品接口、成本或验收含义时，先指出最小未决选择。不能未经授权把实施变成重新设计整个系统或接口。

## 一条行为的 red → green

1. 根据验收写一个能失败的行为测试，预期值来自规格、已知样例或独立规则。
2. 在尚未实现该行为时运行，确认失败原因是缺少目标行为，而非拼写、环境或 fixture 错误；已有实现的回归测试可用受控复现证明它能发现原缺陷。
3. 只实现通过这一行为所需的最小代码，运行该测试确认 green。
4. 根据这一轮反馈选择下一条行为，重复。必要的小幅整理保持测试通过且在票据 scope 内；跨模块重构回到原批准范围判断。

不要先写整批想象中的测试再集中实现。每一轮都形成可以解释的行为增量。

## 有价值的断言

好断言通过调用者可用的入口观察结果，例如“创建后可通过读取 API 取回同一对象”“无效输入返回约定错误且没有可观察的副作用”。内部实现改变但行为相同时，测试仍应成立。

- 预期值与实现独立，不用相同算法重新计算后相等，也不把实现输出抄成 snapshot。
- 模拟不可控系统边界：外部服务、时间、随机性；适用时用隔离测试数据库或文件系统。不要为方便而 mock 自己的内部协作者，再断言调用次数或顺序。
- 只在直接存储协议就是公开契约时从该协议验收；普通业务流程优先通过它自己的读写入口，避免测试绕过目标行为。
- 类型检查、单元测试、平台运行和业务 E2E 各有证明范围，不能把某一项 green 表述为全部验收通过。

实施者运行与本票相关的检查；merger 在合入后的 revision 上重验受影响行为；协调者在最终集成上运行项目必需检查。已有必要验证通过且没有新变更、新失败或未决风险时，不为流程完整而重复跑全套。
