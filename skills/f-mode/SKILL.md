# f-mode: 显式开启，按目标选技能

首行内联带上 🥷，不要单独起段。

## 交付约定

- 目标: 用户显式开启后，按目标自动挑最合适的技能把事办完，不用记住每条命令。
- 完成条件: 开关状态已确认或当前已按选定技能完成任务；没能完成的，把缺口说清楚。
- 依据: 用户目标、当前有效授权、已安装技能的适用范围，以及本轮实际读过的原则。
- 交付形式: 开关时一句确认；执行时先说选了哪个技能再给结果，工程原则只在真的改变决定时提一句，没影响就不提。

## 会话开关

默认关闭。只有用户输入 `/f-mode`、`$f-mode`、`/fskill:f-mode`、`/fskill f-mode` 或明确说“进入 f-mode”才开启。安装、加载技能、文档里引用或聊起 f-mode，都不算开启。

这几个入口都支持 `on`、`off`、`exit`、`status` 参数；下文统称 `/f-mode`。单条技能随时可以直接调，不用先开模式。

- `/f-mode on` 开启；`/f-mode off`、`/f-mode exit`、`退出 f-mode` 或用户要求停用时立即关闭。先处理开关再看任务；关闭命令里顺带提了任务时，按普通请求处理。
- `/f-mode status` 只报当前开关状态。只开启没给任务时，确认一句等下一条指令。
- 开启后只对当前会话有效，直到用户退出；完成一个任务后接着提新要求不用重输命令。直接输 `/hunt`、`$write` 等单条命令优先执行，不关掉 f-mode。
- 新会话默认关闭。上下文压缩只记录当前开关、在用的技能和授权边界；旧 HANDOFF、记忆或仓库文件不会自动开启。状态拿不准时当成关闭。

这只是 fskill 的会话约定，不是宿主原生模式。不会改 Plan Mode、工具权限、模型配置或全局规则，也不会跨会话写开关文件。

## 选路与执行

开启时先读 [技能路由](references/routing.md)，挑最贴合的一条工作技能（询问 fskill 用法时转 `f-help`），别把 f-mode 自己又选成子技能。按宿主技能目录读选中技能的完整 `SKILL.md`（Desktop 包读根文档对应章节），只加载这次真用得到的 references，别把全部技能塞进上下文。

动手前用一句话说清选了哪条（比如“用 hunt 查根因”），这就算满足子技能的进入条件。没开 f-mode 时，`think`、`hunt`、`check` 可以按任务自动进入，其余技能必须用户自己点名。

`catchup` 选中后只做只读汇报，不当成 f-mode 的参数或每轮必跑的过场。任务已经明确、校准后就能做的选 `think`，由它走校准模式。少了哪个技能就直说，别在路由器里自己编一套替代流程。

- 给了 URL 先看实际目的（读单份材料通常走 `learn`），别光因为出现链接就切技能；普通改代码、解释概念或小修小补不沾边就直接干，别硬套任务图或验证指南。缺技能时照常靠本身能力推进，别擅自安装或下载。
- 同一目标下可以按需要切技能，每次切换说一句理由；做完用户要的就停。别修完 bug 就顺手发版，也别干完活就自动写复盘、改长期规则或建外部单子。
- f-mode 开着时，子技能里“建议改用 / 建议显式调用下一条”的提示允许由 f-mode 自动接过去；但子技能原本的职责、禁区、只读约束和授权边界照样算数。关掉 f-mode 后恢复各自的单条规则。

## 原则与决策

遇到工程取舍或验证拿不准时，读 [原则索引](references/principles.md)，只按触发条件去读用得上的原则正文。用户在已开启的 f-mode 里点名某条原则时，优先核对那一条；光提原则名字或引用示例不能开启模式。

读了某条原则的依据，不等于顺便把那个技能整个执行一遍（比如读了防复发原则，不能把修 bug 顺手扩大成改 `AGENTS.md`）。缺正文就说明缺口按常理做，别下载替补，也别装作读过没读过的文件。普通问答和开关状态不用提原则索引；只有真的改变一处具体决定时，顺手点明哪条原则、改了什么和依据即可。

## 硬性规则

- 选中技能不等于拿到操作授权；让给方案就只交方案，改代码、push、发版和对外发消息都看当前任务的明确授权。
- 不因此自创并行 agent、指定模型，也不假装有 Cursor 那种常驻 mode 接口。任务本身已授权且宿主支持的执行方式照常用。
