# 编排与恢复

首次实施、重启、冲突或验证失败时读取。单一协调者拥有整个任务图，实施者只拥有已认领的票；merger 负责串行改变集成分支。

## 项目适配与账本

沿用项目已有票据、分支和验证约定；配置缺失时把本地账本放在已有任务目录，没有约定时使用 `.scratch/<feature>/execution.json`。账本与票据互相指向，不复制整段讨论。创建前检查目标是否已有内容。

至少记录：规格/批准指针、集成分支及当前 head、协调者 owner 和本次 run、逐票 blocked_by/owner/状态、实施分支与 worktree、基线 commit、待合入 commit、集成 commit、验证证据与 tracker 状态。关键选择、拒绝路线、pivot/revert 及其理由和证据也写入现有账本或其决策记录，每项关联产生它的 run 与 owner；纠正旧决定时保留原记录并指向替代项，接手不能覆盖旧 run 身份。账本与锁使用同一协调位置的规范路径，实施 worktree 只引用，不各自复制；不为普通微编辑再造流水日志。

使用宿主已有认领或锁能力；没有时先用原子创建协调锁目录（如 `mkdir <任务目录>/.coordinator-lock`）取得唯一 owner，再记录身份与派工。创建失败就读回原 owner，不覆盖锁或重复派工；接手时只有确认原执行停止且完成移交，才释放已知锁。正常结束时，持有者在保存最终状态且确认无活跃执行者后释放自己的锁。每次派工前读回 owner，不能仅靠内存里的列表防止重复启动。

检查器接受以下最小 JSON；其他字段可以保存上述指针：

```json
{
  "tasks": [
    {"id": "01", "blocked_by": [], "status": "pending"},
    {"id": "02", "blocked_by": ["01"], "status": "pending"}
  ]
}
```

从本次加载的 Implement 目录定位 `scripts/task_graph.py`，执行 `python3 <技能目录>/scripts/task_graph.py <execution.json>`。脚本不修改状态、不运行 Git 或测试；成功返回 JSON 中的 `ready`、`blocked`、`in_progress`、`awaiting_integration`、`invalidated`、`needs_recovery`、`verified` 和 `complete`。已开工但 blocker 不再 `verified` 的票进入 `invalidated` 与 `needs_recovery`，不列入可继续集成的队列；协调者仍须核对执行者并暂停受影响合入。无效图返回非零并说明错误。`complete` 只表示账本中的所有票满足证据字段约束，仍须由协调者读回实际事实。

## 状态与解锁条件

| 状态/事实 | 进入条件 | 是否解锁依赖 |
|---|---|---|
| `pending` | 已批准且尚未认领，或明确恢复为可重试 | 否 |
| `running` | owner、基线与工作位置已保存，执行者已接手 | 否 |
| `done` | 实施者提供 commit、验收结果与限制，等待集成 | 否 |
| `merged` | commit 已进入指定集成分支，验证尚未通过 | 否 |
| `verified` | 合入后的行为验证通过，证据与 integration commit 对应 | 是 |
| `failed` / `blocked` | 执行、冲突、环境或验证阻塞，记录原因与恢复动作 | 否 |
| `tracker_status` | 外部或本地 tracker 自己的开放/关闭状态 | 不参与解锁 |

写入 `verified` 前，协调者核对实际集成分支包含交付 commit、工作区没有混入未知改动，验证确实在所记 revision 运行且结果通过。保存形如：

```json
{
  "id": "01",
  "blocked_by": [],
  "status": "verified",
  "integration_commit": "0123456789abcdef0123456789abcdef01234567",
  "verification": {
    "commit": "0123456789abcdef0123456789abcdef01234567",
    "result": "passed",
    "evidence": "<验证日志或可读回的运行结果指针>"
  },
  "tracker_status": "open"
}
```

`integration_commit` 使用 Git 读回的完整 commit ID，不用分支名代替。后续集成提交必须保留先前交付；发生 revert、修改或相关验证失败时，撤销受影响票的 `verified`，并把已解锁下游标为需要重验，不能继续沿用失效证据。

验收预算、容差、allowlist 或必需检查被放宽时，先保存原门槛、失败证据、变更理由和适用范围；改后的通过结果不能证明原目标已满足。取得非修改者的验证证据，再由协调者读回证据并记录新复核及适用 commit，才能采用新门槛；复核需证明真实需求仍受保护，而非只让结果变绿。没有独立验证能力时保留待复核。协调者复核只覆盖已有授权内的调整，不代替用户或平台要求的批准，也不允许绕过强制检查。

## 准备与认领

1. 读回规格、票据、已有批准和账本；读取当前 branch/head、status（含 untracked）、worktree 列表和现有执行者。确认原协调者是否仍活跃，不能凭账本时间久就判断失联。
2. 原协调者活跃时不重复派工；接续它的现有执行或在需要时明确移交。owner 无法判定时，只暂停重复认领，仍可只读核对图、分支与证据。
3. 选择集成分支：用户指定或项目已有的有效分支优先；需新建时遵循仓库命名，从明确基线创建并记录完整 commit。当前 checkout 有无关 dirty 改动时，保留现场，使用适合的干净隔离位置，不 stash 或 reset 未知工作。
4. 逐票认领前重算前沿，只认领 `pending` 且所有 blockers `verified` 的票。保存 owner、基线、预计文件范围与验证入口后再派工。并行度以宿主能力、真实独立性和共享资源为限，不为了占满 slot 制造并行。

无并行能力或只有一张小票时，可在合适的当前工作位置串行实施；记录实施基线与集成 commit，直接完成同样的验收门槛，无需创建无收益的额外分支/worktree。

批量或未知配方先选一个完整、可验收的 pilot，检验接口、工具和验证成本，再决定是否扩展并行。确有重复机械劳动才建 helper；先用同一单元对照手工结果。执行者完成后可按最新前沿滚动补位，不为了等待整批结束闲置独立工作。

## 实施者与共享文件

### 派工契约

交给实施者：规格和单票指针、已有研究/接口决定、当前集成基线、owner 范围、阻塞、验收与命令，以及不得进行的未授权外部动作。通信优先用文件、票据和 commit 指针；只补充现有材料没有的差异。

并行实施者的隔离分支必须基于所记集成分支 revision。开工前读回基线与 dirty 状态；发现基线错误时在干净且归属清楚的工作位置重新建分支或按项目流程同步，绝不为了匹配基线 reset 未知改动。

两个票可能改动同一文件时，在派工前分配 ownership：

- 能通过稳定接口独立实施的票，各自改自己的模块；接口提供者先交付兼容契约。
- lockfile、生成物、聚合注册表等共享输出由一位 owner 在合入阶段统一更新，其他实施者交付其源变更。
- 无法清楚隔离的共享行为串行安排，并记录真实的依赖或资源约束，不伪称可以无冲突并行。

实施者报告包括票 ID、branch/worktree、基线与提交 commit、行为变更、运行过的验收/验证及实际 revision、测量方法、未覆盖条件和共享文件差异。报告 `done` 前核对集成分支是否前进；需要同步时采用项目允许且不会覆盖未知工作的方式，同步后重验受影响行为。

## 合入事务

merger 可以是协调者本身；若委派 merger，仍由协调者保存状态并确保同一时刻只有一个合入事务。

1. 读回集成分支 head 与工作区状态，确认待合入 commit/基线属于本票；保存合入前 head。
2. 审阅实际 diff 与票据 scope，再按项目方式合入。冲突交由相关 owner 按已定接口解决，不能默选 ours/theirs；有未定语义冲突时记录最小阻塞。
3. 记录新 head，状态改为 `merged`。在这一 revision 上运行本票、受影响依赖和共享生成物的必要检查，确认无未知工作混入。
4. 通过后保存同 revision 的验证证据并改为 `verified`，再派下游。失败则记录 `failed`，冻结受影响前沿并进入恢复；没有证据时保留 `merged`，不把“稍后补测”当完成。

完整独立审查放在代码可审时；rebase 或局部修正后按实际 delta、基线、依赖和检查配置重验受影响语义，通常由一位验证者完成，无委派时直接检查。新增行为、架构变化、共享边界变化或覆盖不足时扩大审查，不机械地每次重开整组 reviewer。新结论绑定当前集成 commit；旧记录保留原 revision，patch-id 相同不证明新基线上的行为或产物相同，项目必需检查不能因缩小审查而省略。

合入不能完成时，只中止自己发起且归属明确的 merge/rebase 操作，保留交付分支；不 reset 集成分支来抹去未知改动。合入已完成但需要撤销时，先核对后续依赖与批准范围，在明确归属的分支按项目方式生成可审阅修正或 revert，再重验和更新账本。

## 失败与中断恢复

| 现场 | 恢复动作 |
|---|---|
| 实施者消失或宿主中断 | 读回其 branch/worktree、未提交文件和已产出 commit；确认原执行已停止或完成移交后才更换 owner |
| `done` 但尚未合入 | 核对交付 commit 仍存在、scope 与基线，接续 merger；不重做整票 |
| 已合入但没有验证记录 | 从 Git 读回合入 commit，在当前有效集成 revision 验证并记录新证据；不凭旧“通过”补写 |
| 测试或环境失败 | 区分行为回归与环境缺口，记录失败命令、revision 和原因；修复可推进部分，受影响票保持非 `verified` |
| tracker 写入失败 | 保留已验证代码状态，读回外部现状再补未完成操作；不要重复建票/PR或把失败当已关闭 |
| 下游已经基于后来失效的上游开工 | 暂停其合入，通知 owner 核对新基线，重验受影响行为；不销毁已完成工作 |

中断前保存：协调者状态、活跃执行者与 owner、每票现场、未完成的合入事务、最后有效集成 head、验证证据、下次动作。恢复先核对实际 Git、宿主执行者与 tracker，再更新账本；旧账本是定位线索，不覆盖当前事实。继续沿用的旧证据保留原 run 与适用 revision，本轮新验证另记身份，不能把继承记录写成本轮执行。

停令传达给所有相关执行者并核对实际停止。每个已派子任务都要收束为已交付、已吸收、取消/失败或具体缺口；退出和沉默不等于通过。迟到结果先核对当前 owner、head、已有替代交付和证据，不重新启动过期派工或重复合入。

## 收尾边界

完成最终规格验收和项目必需检查后，分别报告“代码已集成并验证”与“tracker 已关闭/PR 已创建”。是否 push、创建或更新 PR、关闭父票以本任务已有授权为准；配置中写着如何操作并不授予执行权限。

收尾回读实际执行轨迹、Git 与产物，确认账本的保留/拒绝/撤回、每个子任务终态和最终 head 一致；只靠实施者摘要不能证明全图完成。

长任务检查点发生有意义的变化时，按已安装 catchup 的汇报规范向用户说明进展、阻塞与待决事项；通过宿主技能目录读取其正文，缺少时用同样的简短事实汇报。这里只引用输出规范，不启动只读 catchup 流程或中止仍可推进的已授权工作；无变化时不重复播报，不为汇报新建调度器或修改会话开关。

清理前逐一核对路径是本任务创建且记入账本的 worktree、无 dirty/untracked 工作、提交已有可恢复指针且没有活跃执行者。仍有 open 或 draft PR 的工作现场保留；无法核实远端状态也不判断可清理。条件不满足就保留并报告；禁止递归清理未知目录或为清理而 force 删除。没有外部收尾授权也可以交付本地已验证结果，明确待办即可。
