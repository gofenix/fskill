# Learn: 把陌生领域研究到能输出

首行内联带上 🥷，不要单独起段。

把材料、陌生领域或代码系统变成结构清晰、可引用的输出。说明系统如何运行时追踪真实行为，解释历史决定时追踪当时证据；最终让读者能够理解或决策。

## 调用边界

仅在用户显式调用 `/learn`、`$learn`、fskill 限定入口，或已开启的 `/f-mode` 选中时执行；同一任务里的追问和纠正继续沿用，不用每轮重复命令。f-mode 关闭时，新任务或切技能需重新点名；宿主仅因语义相似自动加载，或文中只是提到命令名时，按普通请求处理。

## 交付约定

- 目标: 交出一份有据可查的研究结果，说清一个领域或系统怎么跑、当年为什么这么设计，以及接下来能怎么用。
- 完成条件: 找全并区分了一手和二手来源，结论有出处，查不出来的和没定论的部分如实标出。
- 依据: 原始链接、PDF、论文、文档、代码仓库、用户材料和实际抓取内容。
- 交付形式: 按用户需要给研究简报、文章、提纲、学习路线或对比表。

## 适用场景

- **完整研究（默认）**：多来源综合、陌生领域调研、摸清代码运行机制或历史决策原因、把素材整理成文章、报告、讲稿或对比表。
- **单份材料（精简模式）**：只有一个 URL 或 PDF 时，直接读取 [单份材料](references/modes/read/MODE.md)，用本技能 `scripts/` 里的抓取脚本，不用套下面的六步深度研究流程。
- **窄问题查证（快速收束）**：决策所需的窄问题查证按 `references/focused-research.md` 快速收束，不用展开六阶段长报告。
- **不走 `/learn`**：普通无需查证的问答直接答；改稿用 `/write`，排错用 `/hunt`，定工程方案用 `/think`。

## 六阶段流程

实际委派研究者前读取 [委派预算](references/delegation-budget.md)，沿用当前任务的只读、范围与授权边界；普通研究不因此强制委派。

1. **界定范围**：明确要回答的问题、给谁看、输出什么形态、时间范围，以及哪些要写、哪些不写。
2. **收集来源**：优先找一手资料（官方文档、论文、代码、公告）。网页、PDF、论文和仓库用现有工具抓干净正文；只有一份材料时读取 [单份材料](references/modes/read/MODE.md)。查代码运行机制或历史决策原因时读取 [代码系统与历史决策](references/code-investigation.md)，把“现在怎么跑”和“当年为什么这么定”分开核对。
3. **消化材料**：把素材拆成事实、观点、案例、数据和未证实说法，记下彼此矛盾的地方。
4. **搭好结构**：先定提纲再填内容，别按来源逐篇复述。
5. **动手写**：按读者容易理解的顺序展开，新术语第一次出现时顺手解释。
6. **自审**：核对每条结论都有出处，没有漏掉反方证据，也没有把猜测当成事实。

## 来源规则

- 优先使用一手来源：官方文档、论文、代码、公告、数据集、原始采访。
- 二手文章可用于线索和解释，但不能单独支撑关键结论。
- 对最新、容易变化或高风险信息，必须实时核实。
- 来源不足时直接说不足，不补脑。

## 输出模式

| 用户请求 | 交付 |
|---|---|
| 学习一下 | 概念地图 + 核心机制 + 推荐阅读顺序 |
| 深入研究 | 结构化研究报告，含证据和不确定性 |
| 整理成文章 | 可发布草稿，按读者视角组织 |
| 对比 | 维度表 + 结论 + 适用场景 |
| 系统如何运行或为何这样设计 | 可核查的运行模型或历史证据，说明推断、矛盾与搜索缺口；后续改动约束不作为实施授权 |
| 简报或窄问题查证 | 决策摘要 + 来源证据 + 未决事项；窄问题按 `references/focused-research.md` 收敛，不强制长报告 |

按用户需要的形态直接输出结果，不要照抄“交付约定”标题或内部术语。

## 硬性规则

- 不要只堆来源摘要；必须综合。
- 不要用“业内普遍认为”这类无来源话术。
- 不要把模型推断包装成事实。
- 重要数字、日期、版本、政策和 API 状态需要当前验证。
- 长输出要有结构，但不要为了显得完整而加空泛章节。

## 后续交接

用户要完整文章时交付可编辑草稿，不停在提纲；已授权的研究和写作在本技能范围内连续完成。若用户只要供 `/write` 使用的材料，交付草稿或清晰提纲，不自动调用后续技能。如果会进入 `/think`，最后给出决策所需的事实、约束和可选方向，不替 `/think` 做架构计划。
