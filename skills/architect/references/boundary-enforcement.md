# 把已选边界落成可执行检查

仅在用户已经选定边界，并授权实施访问约束或相关代码改动时读取和执行。只读架构诊断不提供安装依赖、修改 CI、移动目录或添加文件的权限。

## 先写清要约束的事实

确认模块在哪里、哪些入口公开、哪些内容私有、谁是真实消费者、测试是否有特定允许路径，以及现有层级或循环约束。接口私有性、依赖方向和禁止循环是不同约束；只实现已经选定且有依据的部分，不一揽子改造仓库。

沿用项目既有包边界、语言可见性、导出配置、lint、编译器或依赖检查工具。已有配置中合并最小规则，不覆盖原约束；工具无法表达必要边界时才考虑小脚本或新依赖，声明它的运行条件。

完成条件：边界、消费者、允许例外、实际检测工具和运行入口都已明确。目录形状只是线索，不是边界定义本身。

## 覆盖真实消费者

检查范围要包括会访问模块的应用入口、其他包、脚本、任务、生成代码和相关测试；只扫描包目录可能漏掉从应用代码绕过入口的 import。遵循实际 resolver，核对相对路径、别名、包导出与再导出能否绕过规则；不要靠一个看似正确的 regex 宣称覆盖所有调用。

如果项目选择“根文件公开、子目录私有”，允许多个确有用途的小入口，而不强制单一 `index` 或整体 re-export。如果项目选择另一种公开范围，按其约定表达，不硬迁移到固定目录。

需要从内部测试访问私有内容时，明确该例外的目的和范围；面向使用者的行为测试仍应覆盖公开接口。例外不能让生产代码经测试 fixtures 绕过边界。

完成条件：检查输入覆盖所有已知真实消费者，规则区分正常访问与越界，例外有明确理由。

## 证明检查会阻止违规

1. **先绿**：运行当前相关检查，确认已有合法代码通过；现有失败先区分来源，不用扩大允许范围消除真实违规。
2. **隔离最小违规**：在隔离临时工作区或可可靠恢复的临时文件中添加一个确实来自目标消费者的越界访问。记录临时改动，避免覆盖用户文件；存在不同规则分支时用最小代表案例检查其覆盖。
3. **观察变红**：使用同一个真实检查入口运行，确认因预期边界规则失败，指向越界位置；语法错误、未解析模块或工具未安装导致的失败不算证明。
4. **移除再绿**：只移除自己引入的违规，恢复后再次通过；检查 diff 确认没有留下测试性违规或损坏用户改动。

完成条件：观察到合法访问通过、最小越界被预期规则拒绝、恢复后通过。只写了配置或只观察绿色，不算完成；无法安全做负向验证时说明缺口。

## 接入既有入口与导航

在授权范围内接入项目现有检查命令和 CI；没有现有汇总入口时提供直接运行方式，说明尚未接入的部分。只在确有必要时补最小边界说明与导航，不创建装饰性示例包、重写目录、增加别名或无关框架。

完成条件：贡献者能从已有文档发现约束，执行明确命令，收到可理解的越界错误；配置和 CI 的实际状态已读回。

这些检查证明指定访问约束有效，不能证明语义深度、业务行为或生产集成正确；相应行为仍按实际改动做必要验证。
