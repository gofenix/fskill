# 面向具体读者的写作交付

仅在需要下列交付时读取对应部分；语言和作者声音仍遵循入口及对应语言参考。

## 技术文档的目的

新写或已授权调整结构时，先用 Diátaxis 区分读者正在学习还是工作、需要行动还是理解，再选择合适内容：

| 目的 | 内容重点 |
|---|---|
| Tutorial：通过操作学习 | 说明会做出什么，步骤有可观察结果，必要解释不打断练习 |
| How-to：完成具体任务 | 从读者目标组织步骤，列明条件与分支，背景另给入口 |
| Reference：查找准确事实 | 按对象结构呈现选项、限制和错误；能从权威来源生成时避免手工同步 |
| Explanation：理解原因 | 围绕一个问题说明背景、约束、设计决定和替代取舍 |

整份文档或不同章节可以有不同目的；先使每部分服务明确的读者需要，必要时拆分并相互引用，不机械规定一页只能有一种内容。只获准润色时保留已有结构，不借分类重写教程或补造结果；措辞与技术语义仍按对应参考处理。

## 发给他人的问卷

先弄清收件人的角色、掌握的信息和作者希望借回答做什么决定。向作者追问收件人背景，不让作者代答本应询问收件人的问题。能从已有材料取得的信息先查，问题按决策价值排序，必要时区分必答与可选；允许部分回答或“不知道”，不要用问题暗示期望结论。交付可直接发送的文本，起草不等于发送授权。

## PR 描述

从最终 diff、真实需求和实际验证证据写问题与结果，遵循仓库模板。用具体触发和前后行为解释变化；缺少修前执行证据时如实说明，不能造日志。复杂结构只有在更容易审阅时才配最小图示、调用例或前后片段，简单修复可直接用两句话。

按变化风险说明测试、影响范围和回滚代价，区分代码可回滚与数据或外部副作用可逆。内容围绕最终实现重写，删除讨论过程和废弃方案，除非它们解释必要取舍。写好 body 不授权创建 PR、提交或发消息。

## 长文素材与结构

新写长文时，先收集作者原始经历、观察、数据、引用和未决片段，区分作者事实与模型建议。素材阶段可以保留碎片，不急着套大纲；缺独特事实时提出集中问题或缩短范围，不能补造作者经历。

需要重组时保留原始素材，另形成可编辑稿；每段应满足读者的一项理解需要，并让必要概念先于依赖它的结论出现。比较结构时说明目标读者与取舍，不强求每段固定形式。发现缺少例子或证据时向作者列明缺口，不把编辑待办混进最终正文。现有成稿的结构改动仍遵循入口授权，不强制把所有文章拆成素材库。
